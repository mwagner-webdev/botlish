# Post native stack audit

Diagnostic baseline: 20 September 2026, x86-64 Ubuntu 24.04 under WSL, Tcl 9.0.1, rustc 1.98.1 `-O`, Go 1.22.2 `go build`, Cranelift 0.135.2, regalloc2 0.15.2. Source revision `36ebd8a` plus the diagnostic VCode capture correction in this audit. Benchmark inputs and sizes are unchanged. The release native backend was rebuilt before measurement. No code generation optimization was made.

Reproduce the native corpus with `tclsh9.0 native/generate-scalar-audit.tcl -outdir audit/post-native-stack`; reproduce selected HIR/NIR/CLIF/allocation data with `tclsh9.0 native/generate-post-stack-details.tcl`. Reference assembly is in `audit/post-native-stack/refs/`. The benchmark command was `LANG=C.utf8 LC_ALL=C.utf8 tclsh9.0 bench/bench.tcl -runs 5 -markdown`. Every column is best of five after an untimed warmup; native timing excludes JIT compilation. Native timing includes a function invocation and timer, so the 0.5–1.8 µs cases are near the measurement floor. Values agreed across all six implementations.

Rust and Go use fixed-width signed 64-bit integers and do not implement Botlish's arbitrary-precision overflow behavior, error completions, or GC root contract. ## What VCode means here

The previous committed files named `*.vcode` contained CLIF construction log messages (`inserted inst`, `defining function`), not VCode. The corrected diagnostic logger retains Cranelift's `vcode from lowering` record in `machinst/compile.rs`, emitted after x86 machine instruction lowering and before `regalloc2::run_with_ctx`. Registers such as `%v193` are virtual; ABI fixed registers are shown as `%rdi` etc. User stack-map slots and explicit stack-address operands may already exist. Allocator spill slots and its inserted copies have not yet been introduced. The diagnostic fix is checked by `native-vcode-1`. Do not use the older mislabeled files as evidence of allocator behavior.

## Corpus and stack reform

The same 13-program corpus contains 194 native functions (136 specialized, 58 generic) and 89,512 generated machine-code bytes. The closest committed pre-stack snapshot is `c308668`: 108,306 bytes, so 18,794 bytes (17.4%) disappeared. Every program shrank; there is no per-program growth. Largest reductions: `csv_records` 27,901→22,468 (-5,433), `hashtable` 16,680→13,704 (-2,976), `refined-checks` 23,770→21,002 (-2,768), `csv_chunked` 12,690→10,496 (-2,194). The largest individually matched function reduction is 232 bytes in `hashtable` and its `csv_records` inclusion. The four benchmarks changed: fib 680→463, loop-count 702→511, sum-refined 743→452, refined-checks 23,770→21,002. These are object-function bytes, excluding linked runtime/libc and cold constants.

Across the corpus summaries there are 607 safepoints, 665 physical root slots summed over functions, and 176 entry-zero slots. These are static per-function totals, not simultaneous live roots. The NIR corpus has 267 ordinary `call` sites, 32 `callenv`/`callenvmulti` sites (all in `refined-checks`), 29 closure-construction sites, 19 `listget` sites and 23 `listnew` sites. These are static source-lowering sites, not executed counts. The assembly has 1,253 static call instructions; the object corpus shows no indirect `call r*`/memory call at Botlish call sites. Calls to closure-bearing functions can therefore still be direct. This count includes wrappers and cold helpers and must not be interpreted as executed call frequency. `refined-checks` has 31 functions, 16 root slots in `<program>`, and 21,002 bytes; startup is unusually large because it creates a 16-element hex digit List and a closure for `web::uri_escape_text`.

The stack reform removed per-call shadow-depth reservation, `ss_top`/`ss_limit` testing, depth-token writes/restores, and the cold `rt_stack_overflow` call from supported x86-64/Linux functions. Representative fib assembly now starts with `push rbp; mov rbp,rsp; sub rsp,0x30` and one required root-slot zero store. GC roots are physical slots in native frames, discovered through Cranelift stack maps and the native frame walker; describing this as the old shadow-stack push/pop protocol would be wrong. Ordinary calls still publish live roots to native-frame slots, obey SysV argument/result registers, preserve callee-saved registers when used, check the Botlish no-value error sentinel, and maintain the frame pointer. The frame pointer is a Cranelift configuration constraint. Root publication and completion tests are Botlish runtime/ABI requirements until facts prove them unnecessary. The source-level libc/pthread discovery occurs before JIT execution; it is not recurring hot-path work.

The x86-64/Linux stack fast path has **zero explicit generated guard instructions** for ordinary small frames. A guard-page SIGSEGV/SIGBUS on the dedicated pthread is handled on an alternate signal stack and terminates the process with the established stack-limit error protocol. Large frames use 4 KiB inline probes; the repository's large-frame fixture exercises them. Go's compared recursive functions have `CMPQ SP, 0x10(R14); JBE morestack` at entry, plus a cold growth path. Botlish's zero-instruction common path is cheaper than those two Go instructions, while the overflow recovery models differ. The transitional pthread/libc dependency is accepted architecture, not a performance finding.

## Hot-path attribution

### sum-refined: microscope

HIR knows the accumulator is `int` inside the refinement branch, and the specialized `sum<int,int>` NIR removes `integer?`. It carries `n` as raw and tail-recursion becomes a loop. Yet its local `step` remains `step<generic>`: NIR has `guard int %0` and `iadd %0 %1`. The call result is tagged. That is the main compiler opportunity, independent of the stack change.

| Semantic operation | Botlish final x86-64 | Rust `-O` | Go 1.22 | Origin / classification |
|---|---|---|---|---|
| termination | `test rbx,rbx; je exit` | `test rdi,rdi; je` | `TESTQ AX,AX; JNE` | A, same work |
| form next n | `sub rbx,1` on backedge | `dec rdi` | `LEAQ -1(AX),CX` | A; Botlish moved it after call |
| form step argument | `shl rdx,1; or rdx,1` | raw `add` | raw `ADDQ` | B/E: tagged argument required by generic step ABI; avoidable if a specialized raw step is proven |
| root publication | `mov [rsp+8],rdx`, then `mov [rsp],rax` | no GC root | no GC root | C; two slots, one safepoint; published values are live around the call |
| invoke step | direct `call botlish_fn_2` | closure inlined, recursive call | closure inlined, recursive call | D: missed closed local call specialization/inlining; total call counts are not directly comparable because Rust/Go retain recursion |
| step type guard | `test rsi,1`, pointer-kind path, branch to cold `rt_type_error` | absent | absent | D/B: Botlish type check is required for generic entry, but caller already passes refined `int` |
| step add | tagged `and/test`, `lea/add/seto`, cold `rt_int_add` | raw `addq` | raw `ADDQ` | B/D: BigInt fallback necessary for unproved generic operands; existing caller range does not reach step |
| completion | `test rax,rax; jne` after call, error exit | absent | absent | B/C: Botlish error completion; candidate only if callee totality can be proved |
| loop-carried copies | `mov rsi,rax; mov rax,rbx; mov rbx,rax` around backedge | no corresponding loop | no corresponding loop | G/F candidate: VCode has block parameters and explicit jumps; some physical copies appear only after allocation. Do not assign every ABI move to regalloc2. |
| frame | `push rbp`, 32-byte frame, save/restore `rbx,r15` | recursion pushes one word around `black_box` | frame pointer, 16-byte frame, entry stack check | C/F/J: frame and reference control-flow shapes differ |

The actual VCode already contains the tagged-argument `shlq/orq`, root stores, call, and completion `testq/jnz`; these originate at NIR or the Botlish ABI. It also contains the generic step guard and checked add, so they are not allocator inventions. It contains more unconditional empty-block jumps than final assembly: Cranelift's later layout removes many. The final `mov rbx,rax` on a loop-carried copy has no explicit VCode move of that exact physical shape, but one isolated copy does not establish a new allocator bug. The `rt_int_add` call is cold on the benchmark input; the tag/overflow tests execute each step. The function is allocation-free (three static constant-table objects, 189 bytes).

Conceptual Botlish minimum for this *proven* call would be condition, raw decrement/add, any required completion check, direct call or inlined step, and native root publication only for values actually live at a MayGc call. A generic public step must retain its guard and BigInt fallback. This distinction keeps the arbitrary-precision contract separate from the missed caller facts.

### loop-count: control flow and timing floor

The leaf `work<int>` is 54 bytes, no root slots, no safepoint, no helper call. It unboxes `i`, computes `3*i+7`, tests sign, returns tagged 7, or loops forever on the negative path. VCode has the same arithmetic and branch; final assembly is compact apart from mandatory `rbp` setup. The operation is not safely replaceable with a constant for *every* arbitrary-precision input; the finite input range makes the benchmark path simple. Rust reduces the common contribution and Go inlines `work`, so neither is a literal lower bound on Botlish's full semantics.

The outer `drive<int,int>` still calls `work` each iteration, then tests completion and performs tagged addition with a cold `rt_int_add` fallback. VCode already has the tag/overflow path. The result of `work` is always 7 on its returning path, but that fact is not propagated through the call, so this is a D-layer call-result fact loss, not an allocator spill. There are 500 iterations. At 1.80 µs, dispatch/timer overhead is a material fraction of the observed gap to 0.60/0.80 µs references; no cycle-level claim follows from these numbers. The remaining scalar work is explained by the call, completion, tagged addition, and source semantics, not by a mysterious hot runtime call.

### fib: recursive call/stack stress

For n=22 there are 57,313 function invocations (including leaves). A simple difference divided by that count gives about 2.64 ns/invocation against Rust and 2.08 ns/invocation against Go (193.93−42.76 and 193.93−74.64 µs respectively). This is a sanity scale, not a causal or cycle-accurate allocation of time.

Botlish's `fib<int>` is 393 bytes including its entry wrapper. Its recursive fast path has no explicit stack-bound compare. It has frame-pointer setup, 48-byte frame, callee-save work, one entry root zero, tagged-to-raw n conversion, two raw decrements and retags for arguments, two direct recursive calls, two no-value checks, root stores, and a tagged/overflow checked result addition with cold `rt_int_add`. VCode contains these operations before allocation. Rust uses fixed-width raw arguments/results with no Botlish completion/GC work. Go uses raw operations plus a two-instruction per-entry stack guard and cold `morestack` path. Rust and Go both omit tagged addition and completion; their integer/error contracts allow it. The surviving Botlish checked *result* addition is a candidate D-layer range-proof issue only if recursive result bounds can be established; the current HIR does not establish them, so the fallback is presently a legitimate B cost. The source-reported regalloc2 pattern also appears in fib's argument retagging copies; classify these copies as G, not a reason to contort Botlish NIR.

### refined-checks: allocations before instruction tuning

One measured native run allocates 20,819 managed objects / 980.1 KB, with peak live equal to that total and no GC cycle. Strings: 13,609 objects / 566.8 KB; Blocks: 7,205 / 413.0 KB; Lists: five / 288 B. The top two `char_at` substring sites alone allocate 9,200 and 4,400 objects (566.4 KB together). Several closure sites each allocate 400–800 Blocks. String copying is 22.4 KB, List copy volume 21 elements. These are executed-site counts, unlike static assembly calls.

The current NIR shows `web::uri_escape_text` holding a managed hex-digit List capture, `esc_from/esc_char/esc_bytes` nested closures, `encode_utf8`/List operations, and two validator families for successful and failing cases. Dynamic `Emailish?` remains a real validator; the earlier native-predicate capability gap is gone. Rust/Go references use native strings/byte slices and do not implement identical Unicode/error/object contracts, so the 10× timing headline does not isolate register quality. Primary costs are String substring construction, immutable construction/concatenation, closure creation, validation, and byte-list intermediates (H/B/D/E); instruction selection is a lower-priority hypothesis. The 31-function NIR contains generic/specialized pairs around the validator and duplicate `char_at`/scanner families. These may reflect two source call sites and differing result shapes; duplication is visible, but an accidental specialization rule has not been proved. `<program>` creates the module capture once, while nested closures recur.

## Modules, calls, and previous findings

`web::uri_escape_text` is a managed-capture module function (`env=1,captures=1`). Its initial `callenv 1` in NIR is a direct `botlish_fn_1` relocation in final x86-64. The environment object and captured List are set up at startup, and the body loads its capture; no dynamic target dispatch remains. The matched `audit/post-native-stack/module-cases/` probe adds `plain::inc` (envless), `scalar::add` (one immutable Int capture), and `managed::get` (one immutable List capture). All three compile to direct calls. The captured values are lifted into hidden direct parameters: `scalar::add` and `managed::get` have `params=2 env=0`, no closure and no `callenv`; the List is built once at startup (40 B). The plain call specializes as `int`, but the scalar-capture call remains `generic` and has an executing `guard int` and checked tagged addition even though the caller passes constant 1 and captured constant 7. This is a concrete cross-module/hidden-parameter fact-loss instance (D/E), corroborating the broader closed-call finding. The managed call also stays generic and retains its index guard and bounds path; those may be required for dynamic callers. The fixture has one call of each kind, so its frequency evidence is narrow. The slight module-era timing movement still cannot be causally assigned to persistent indirect dispatch.

`ht_empty_state()` and `chunk_size()` remain direct calls to tiny literal-returning bodies. For example, `ht_empty_state` is `push rbp; mov rbp,rsp; mov eax,1; mov rsp,rbp; pop rbp; ret`; callers also test the no-value sentinel. The calls did not fold away. They recur in hash probing and builders, but a module binding is now a source/stdlib cleanup (H) with a concrete acceptance check: remove these hot calls without increasing startup capture work. It is below the broad closed-call fact problem.

Current final object call relocations are direct for statically known Botlish functions and known runtime helpers. Some VCode shows `load_ext_name; call *%v` for helpers, yet object final assembly has a direct relocation; this is a **VCode-to-final lowering/linkage difference**, not a hot accidental indirect call. Dynamic ListGet still has inline representation/bounds/load success paths with cold fallback, and StringRegion/traversal work has no obvious regression in the retained corpus. `geo_append`, `chunked_append`, `ht_rehash_scan`, and `ht_rehash_insert` retain widened aggregate signatures; their size and VCode show register/root pressure in large functions, but this audit did not establish a recurrent hot spill count attributable solely to product width. No arbitrary width cap is justified.

Earlier ideas: nullary helpers are still visible but source-scoped; cross-call repeated strlen/bounds and CSV scanner induction limits remain plausible from prior audit but were not remeasured as dominant here; generic inlining is too broad a proposal; call-result range propagation remains visible in `drive` and fib; ListGet and refined predicate native support are superseded by landed work. There is no evidence to revive an old benchmark target merely because an older time was smaller.

[regalloc2 issue #265](https://github.com/bytecodealliance/regalloc2/issues/265) is open and includes a three-case [minimal reproducer](https://github.com/mwagner-webdev/regalloc2-repro). Its fib example shows repeated physical copies into a register overwritten before use around destructive operations. The current fib VCode has virtual arithmetic/retagging chains, while final assembly has repeated `mov r12,rsi` in that region; this is G-layer evidence. The issue is upstream; no Botlish IR workaround is recommended. The old issue body links an artifact mislabeled VCode, so the corrected dump here is the reliable pre-regalloc evidence. No separate Cranelift issue was verified in this corpus.

## Limits and verification

The audit artifacts retain HIR, NIR, CLIF, true VCode, x86-64, Rust, and Go for the four benchmarks; assembly/VCode/roots for the full stdlib corpus; and HIR through assembly plus allocation data for the matched module probe. The VCode is generated through JIT compilation whereas final assembly comes from the object path; both use the same lowering rules, but linkage details can differ, as the helper call example shows. A static call-site census cannot replace a profiler. No separate controlled run quantified the harness floor, wide-product spills, or code layout noise. Those are lower-confidence areas, not optimization recommendations. The native allocation tool excludes BigInt limb buffers and code/runtime allocations; the reported managed counts are not total process allocations.

Verification: `cargo test --release --manifest-path native/Cargo.toml` passed 53/53. After correcting the diagnostic assertion to require `vcode from lowering`, the complete `tests/all.tcl` rerun passed 1,450/1,450 on each of interp and compile. `native.test` passed 89/89 in a focused run. With `BOTLISH_NATIVE_GC_STRESS=1`, `native-root-storage.test` passed 10/10, `native-stack-map.test` 10/10, and `native-stack-overflow.test` 4/4. Benchmark values matched across all six implementations.
