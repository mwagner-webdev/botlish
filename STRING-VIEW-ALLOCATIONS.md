# String-view allocations: closing the `char_at` allocation gap

Milestone date: 22 September 2026. Prior source revision: `33a938e`
("Regenerate the scalar assembly audit corpus"). The post-call-effects
audit's decision **B** ("scalar backend quality is mature enough for now;
move deliberately to String / Bytes / construction") is this milestone's
mandate. Evidence generated by this milestone is under
`audit/string-view-allocations/`.

## Files changed

- `hir/stringregion.tcl` -- new analysis: `ConsumingNative`, `ConsumingShape`,
  `ConsumingParams`, plus extensions to `Bindings` (`classifyArgs`,
  `consumingCallArgs`) and `analyze`/`explain`, and the new query
  `consumingParamsOf`.
- `native/lower.tcl` -- `TryStringRegionOp` extended to lower
  `is_tcl_alpha`/`is_tcl_alnum` of a region-eligible argument directly;
  a new `Call` dispatch branch, `IsRefToBinding`, `EmitRegionConsumerBody`,
  and `InlineRegionConsumerCall`, which inline a region-consuming callee's
  body against a caller's region instead of calling it.
- `native/src/nir.rs` -- two new `OpCode` variants, `StrRegionIsTclAlpha`/
  `StrRegionIsTclAlnum`.
- `native/src/runtime/ops.rs` -- `rt_str_region_is_tcl_alpha`/
  `rt_str_region_is_tcl_alnum` (plus the shared `region_one_scalar` helper),
  `op_may_error` and helper-table entries, four new unit tests.
- `native/src/codegen/clif.rs` -- Cranelift lowering for the two new ops
  (mirrors `RegionCheck`'s dispatch entry exactly: no allocation, RANGE-
  fallible).
- `tests/native-string-view.test` -- 17 new differential/NIR/GC-stress tests.
- `audit/string-view-allocations/` -- generated evidence (NIR, VCode,
  assembly, allocation reports, root reports) for the before/on/off states.

No change to `core/`, `surface/`, `lib/web.bot`, `lib/web.tcl`, or any
`examples/stdlib/*.bot` source. `TextBuilder`, `Utf8Bytes`, string
interning, caching, and general concatenation were not touched.

## `char_at` semantics, before and after

Botlish's String semantics are unchanged: a String is an immutable sequence
of Unicode scalar values; `substring(text, a, b)` (a *scalar* index range,
never bytes) is the only way to extract a sub-range, and `char_at`-shaped
extraction (`substring(text, i, i+1)`) is ordinary library code, not a
distinct language construct. `lib/web.tcl`'s `Emailish?` native-body defines
its own local `char_at(i) = substring(v, i, i+1)` closure; this is the
concrete `char_at` the milestone brief's evidence refers to. `core/
tclcompat.tcl`'s `is_tcl_alpha(c)`/`is_tcl_alnum(c)` remain one-scalar-String
classification natives with the same RANGE-on-wrong-length contract as
before. Nothing about indexing domain, error behavior, empty-string
behavior, or `==` value semantics changed.

**StringRegion before this milestone** (`hir/stringregion.tcl`,
`native/lower.tcl`'s "String regions" section) already recognized a
`substring(text, a, b)` call or a String literal as a "region" (base, start,
end: three registers, never materialized) and could virtualize it through a
local binding, an inline operand, or one level of return-position
forwarding through another instance ("region companion",
`RegionCompanionFunction`) -- but **only** when the region's every use was
an operand of `==` (`streq`) or the sole argument of `length`. Runtime
support: `rt_str_region_check`/`rt_str_region_eq` (`ops.rs`), NIR
`regioncheck`/`regioneq`.

## The dominant allocation families

`bench/refined-checks.ir` (revision `33a938e`, `-string-region-opt`
default on) allocated 20,819 objects / 980.1 KB per run; String alone was
13,609 objects / 566.8 KB, and **13,600 of those 13,609** were two sites
both attributed to `func char_at ... substr` (9,200 and 4,400 allocations --
`audit/post-call-effects/bench/refined-checks.alloc.txt`, reproduced
byte-for-byte at `audit/string-view-allocations/refined-checks/before/`).

Tracing both families through NIR (`audit/string-view-allocations/
refined-checks/before/nir.txt`) shows they are **the same structural cause**,
attributed to two different closure instances of `char_at` -- one per
distinct literal String `bench/refined-checks.ir`'s `check` function is
called with ("café@例え.テスト" and "not-an-email"; `check` recurses 400
times per call, re-running `Emailish?` on the same String each time, so
every character `char_at` ever visits in that String is re-decoded 400×).
`Emailish?`'s native-body defines three scanning helpers that all read
characters through `char_at`:

```
fn scan_local(i):  if is_local_char(char_at(i)): scan_local(i+1) else i
fn scan_label(i):  if is_label_char(char_at(i)): scan_label(i+1) else i
fn scan_alpha(i):  if is_tcl_alpha(char_at(i)):  scan_alpha(i+1) else i
```

`is_local_char`/`is_label_char` are themselves tiny local predicates:
`is_local_char(c) = is_tcl_alnum(c) or c=="." or c=="_" or c=="%" or
c=="+" or c=="-"`; `is_label_char(c) = is_tcl_alnum(c) or c=="-"`.

**Why StringRegion did not eliminate them**: in every one of these three
call sites, `char_at(i)`'s result is the *argument of another call*
(`is_local_char(...)`, `is_label_char(...)`, `is_tcl_alpha(...)`), never
directly an operand of `==` or `length`. `hir::stringregion.tcl`'s
`Bindings` analysis (both its bound and inline-operand cases) only ever
recognized `==`/`length` as consumers; "an argument to any other call"
was explicitly listed as a case that must materialize. So `char_at`'s own
region companion (`RegionCompanionFunction`, already built because the
validator's separate `char_at(i) == "@"`/`char_at(labelEnd) == "."` checks
*did* qualify) existed, but every `scan_local`/`scan_label`/`scan_alpha`
site still called `char_at`'s ordinary, materializing entry
(`callenv 11 ...`, `op substr`) and passed the resulting one-character
String on.

**What each consumer needs**: `is_tcl_alpha`/`is_tcl_alnum` need only a
decoded Unicode scalar (never String identity, lifetime, or byte layout);
`is_local_char`/`is_label_char` need only the same decoded scalar plus
scalar-equality against a handful of literal characters -- again never
identity or lifetime. Neither ever stores, returns, hashes, or concatenates
the character. This is exactly the consumer taxonomy the milestone's #9-10
ask about, resolved per site by direct inspection of each predicate's own
body (`web.tcl:59-80`), not assumed.

## Consumer taxonomy (corpus-wide)

`bench/`, `examples/stdlib/`, and `lib/` were searched for `substring`/
one-character-extraction call sites (`bench/substr_classify.tcl`, extended
by hand for the classification/predicate shape). Every site falls into one
of:

| class | example | before this milestone | after |
|---|---|---|---|
| A. immediate `==`/`length` | `peek(text,i)=="\""` (csv.bot), `Emailish?`'s `char_at(labelEnd)=="."` | already 0 allocations | unchanged |
| B. immediate classification, native | `is_tcl_alpha(char_at(i))` (scan_alpha) | materialized every call | **0 allocations** |
| C. immediate classification, user predicate over `==`/native-classify only | `is_local_char(char_at(i))`, `is_label_char(char_at(i))` | materialized every call | **0 allocations** |
| D. length-only | (subsumed by A) | 0 | 0 |
| E. UTF-8 encode | `esc_char`'s `encode_utf8(c)` (web.bot) | materializes (real substring, escapes into a List) | unchanged (out of scope, #70-71) |
| F. escaping/stored/returned | csv/csv_chunked/csv_geometric/csv_records field values, `string_replace`'s replacement | materializes | unchanged (correctly) |
| G. unsupported predicate shape | a predicate that concatenates, branches on a non-literal, or has >1 parameter | materializes | unchanged (correctly, `view-unsupported-shape-*` tests) |

Classes A/D/F/E were already correctly handled (A/D by the pre-existing
StringRegion; F/E by design, out of this milestone's scope). Classes B and
C are exactly `refined-checks.ir`'s two dominant families, and are the
new work.

## The new representation: an extension of StringRegion, not a new one

Per the milestone's #6, this is a direct generalization of the existing
StringRegion analysis and lowering, reusing its (base, start, end) triple
and its `RegionCheck`/region-companion machinery -- no `CharView`,
`StringSlice`, `TinyString`, or `BorrowedString` was introduced, and no new
Botlish-visible type exists.

**Class B (native classification consumer)**: `hir/stringregion.tcl`'s
`ConsumingNative` names `is_tcl_alpha`/`is_tcl_alnum` as, like `==`/
`length`, natives whose sole region-eligible argument needs no
materialization. `native/lower.tcl`'s `TryStringRegionOp` gained a third
case exactly parallel to its existing `length` case: given a region, emit
`op strregiontclalpha`/`strregiontclalnum` (new NIR ops, `native/src/nir.rs`)
instead of materializing then calling `rt_is_tcl_alpha`/`rt_is_tcl_alnum`.
The new runtime ops (`native/src/runtime/ops.rs`) are a direct
generalization of `rt_str_region_eq`: `rt_str_region_is_tcl_alpha`/
`rt_str_region_is_tcl_alnum` take (base, start, end), reject a region that
is not exactly one scalar wide with the *same* RANGE message
`one_scalar`/`CheckOneScalar` already produce, and otherwise decode and
classify directly from `base`'s text -- with the same ASCII fast path and
non-ASCII seek-and-record-cost as `rt_str_region_eq`. Never allocates;
`RANGE`-fallible, exactly like the materializing form.

**Class C (a user-defined one-parameter predicate built only from
supported shapes)**: this is the smallest sound generalization of the
"String traversal" section's own precedent (`TraversalAccess`: "lower
directly in the caller, never adding an interprocedural ABI or a companion
call"). `hir::stringregion::ConsumingParams` recognizes a used,
non-generic, non-self-tail-calling instance whose *entire* body is built
only from `if`, a literal/root reference, and a call to `==` (one operand a
String literal), `length`, or a `ConsumingNative` -- i.e. exactly the node
kinds `native/lower.tcl`'s new `EmitRegionConsumerBody` knows how to
re-lower -- as "region-consuming" at a parameter index when every reference
to that parameter is one of those three supported operand positions. At a
direct call site where the corresponding argument is itself region-eligible,
`native/lower.tcl`'s `Call` (new branch, ahead of the ordinary dispatch)
calls `InlineRegionConsumerCall`, which re-lowers the callee's own `if`/
`==`/`length`/classification tree **directly in the caller**, substituting
the caller's region for every reference to the consuming parameter -- never
emitting a `call`/`callenv` to the predicate's own compiled function for
that call site at all. The predicate's own canonical function is otherwise
unaffected (still correct for any other, non-inlined caller); if no such
caller remains, the compiler's existing used/reachable-function accounting
naturally drops it (observed for `is_local_char`/`is_label_char` in
`refined-checks.ir`: see "Downstream effects" below -- not something this
milestone added).

This was deliberately **not** built as a second, parameter-side
"companion function" (an alternate compiled entry taking a region ABI):
that would duplicate the interprocedural-ABI machinery the "String
traversal" section explicitly avoided for the symmetric producer-side
problem. Inlining a *pure*, structurally-verified predicate body is smaller
and, since `ConsumingShape` already proves there is nothing but `if`/
`==`/`length`/classification in it, exactly as sound.

**Which representation, decoded-scalar or StringRegion?** The region
(base, start, end) triple was kept, not a decoded `char`, because the
existing consumers (`regioneq`, `isub`) already operate on a region
directly and a literal-comparison chain (`is_local_char`'s five-way
`if`) reuses the *same* one region for every comparison and for the
classification call -- decoding once as a scalar and threading a `char`
through would have needed a second, parallel set of ops for no
measured benefit. `rt_str_region_is_tcl_alpha`/`alnum`'s internal decode
*is* effectively "decode once, classify" -- it just never surfaces the
scalar as a separate NIR value, since nothing here needs to reuse a raw
scalar across more than the one op that decodes it.

## Materialization, escape, and error-behavior rules

- A one-character result still materializes exactly where it always did if
  it is stored, returned, captured, passed to an unsupported/unrecognized
  consumer, or its consuming predicate does not match `ConsumingShape`
  (`view-escape-1`, `view-escape-container-1`, `view-unsupported-shape-1/2`).
- Bounds/RANGE behavior is unchanged: `rt_str_region_check` still validates
  a `substring`-shaped region at the point an ordinary `substr` call would
  have; the new classification ops raise the identical RANGE message as
  their materializing counterparts on a non-one-scalar region
  (`view-classify-range-1`, `view-predicate-range-1`).
- `Unicode` scalar semantics, empty-String behavior, and String `==` value
  equality are untouched; no region identity is ever observable.
- GC/base lifetime: a region's fields are ordinary tagged/raw NIR registers,
  already rooted by codegen's existing per-register shadow-stack mechanism;
  nothing new was added, and nothing needed to be (`BOTLISH_NATIVE_GC_STRESS
  =1` results below).
- No user syntax changed; `StringRegion` (and this extension) remain purely
  compiler-internal.

## Sequential traversal interaction

`scan_local`/`scan_label`/`scan_alpha` are **not** `hir::traversal.tcl`
loops: `hir::traversal::CharAccessorShape` only recognizes a precise
two-parameter `peek(text, index)` guard-then-`substring` shape, and
`char_at(i)` here is a one-parameter closure over a *captured* `v` with no
guard of its own -- so this milestone's fix is unrelated to (and does not
regress) the byte-offset-carrying traversal optimization. `csv`/
`csv_chunked`/`csv_geometric`/`csv_records`/`string_replace`'s own
`peek`-shaped sites were re-measured (`bench/substr_classify.tcl`,
`audit/string-view-allocations/corpus-summary.txt`) and are byte-for-byte
unchanged: the two optimizations coexist without interaction, exactly as
`hir/traversal.tcl`'s own header already required (it excludes any instance
`hir::stringregion.tcl` wants a companion for). Each of `is_local_char(c)`/
`is_label_char(c)`/`is_tcl_alpha(char_at(i))` decodes the region's one
scalar exactly once per call (`rt_str_region_is_tcl_alpha`/`alnum`'s own
single `chars().next()`; `regioneq`'s own single pass) -- no duplicate
decoding was introduced.

## Downstream compiler metrics

- **Machine-code bytes** (`refined-checks.ir`): 20,986 (prior committed
  state, `audit/post-call-effects/bench/refined-checks.summary.txt`) →
  **20,846** (`audit/string-view-allocations/bench/refined-checks.summary.txt`),
  a small net decrease despite two new ops and inlined predicate bodies:
  removing the `char_at`/`is_local_char`/`is_label_char` *call*
  instructions (argument marshalling, frame setup/teardown at each call
  site) outweighs the inlined region ops' own size.
- **Safepoints/root candidates/shadow slots**: unchanged in aggregate (97 /
  180 / 103 / 28 entry-zero slots, both before and after --
  `audit/string-view-allocations/refined-checks/{before,on}/roots.txt`).
  Per-function comparison (`scan_local`/`scan_label`/`scan_alpha`) shows
  why: each already had exactly 2 safepoints before this milestone -- the
  materializing `char_at` call (`may_gc=true`) and the self-tail
  `tailenv` -- while the call to `is_local_char`/`is_label_char` was
  *already* not a safepoint (the post-call-effects pass had already proven
  those predicates `may_gc=false`, since they never allocate). After this
  milestone, the `char_at` call is replaced by a call to `char_at`'s
  existing *region companion* (`callenvmulti`, still an ordinary
  interprocedural call site, conservatively still a safepoint under the
  current call-effects proof) plus the new non-allocating region ops: the
  allocation is gone, but the call boundary generating the safepoint is
  still there. Reducing *that* remaining safepoint would need the
  post-call-effects machinery to prove the region companion itself
  `may_gc=false` (it plausibly is, since `RegionCheck` never allocates) --
  a natural next step for that pass, not something this milestone's scope
  covers.
- **Function count**: 31 → 27 in `refined-checks.ir`'s emitted NIR.
  `is_local_char`/`is_label_char` (2 predicates × 2 outer specializations)
  no longer have any caller after inlining and were dropped from the
  compiler's existing used/reachable-function accounting -- an incidental
  benefit of the fix, not new machinery this milestone added.
- **`op_may_error`/`op_may_allocate`**: the two new ops are `may_error=
  true, may_allocate=false`, so every downstream pass that already reads
  those tables (root classification, effect summaries) picked them up with
  no code change of its own -- exactly the milestone's #46-47 intent.

## Answers to the milestone's 22 questions

1. **What caused each dominant family?** The same cause for both: `char_at
   (i)`'s result, in `scan_local`/`scan_label`/`scan_alpha`, is passed as
   an *argument* to `is_local_char`/`is_label_char`/`is_tcl_alpha` rather
   than compared/measured directly -- a shape `hir::stringregion.tcl`
   never recognized. Family "A" (9,200) and "B" (4,400) are the same
   structural site, instantiated once per the two distinct literal Strings
   `refined-checks.ir`'s `check` function scans (400 iterations each, one
   `char_at` closure per String).
2. **Why did StringRegion not eliminate them?** Its consumer recognition
   (`Bindings`) only ever accepted `==` (streq) and `length` as supported
   uses; an argument to any other call was explicitly excluded.
3. **What replaces the temporary String objects?** For a native
   classification argument: the region's (base, start, end) fed directly
   into a new non-allocating classification op. For a user predicate
   argument: the predicate's own body, inlined against the region, so the
   *same* region feeds both its literal comparisons and its classification
   call with one shared validated span.
4. **Generalized StringRegion, or something else?** A generalization: the
   same (base, start, end) representation, the same `RegionCheck`
   validation, and the same "canonical function unconditionally correct
   for other callers" discipline, extended to two more *consumer* shapes
   (a native classification argument, a proven-pure predicate argument).
5. **Which consumers operate directly on it?** `==` against a String
   literal, `length`, `is_tcl_alpha`/`is_tcl_alnum`, and a user-defined
   one-parameter predicate built from nothing else.
6. **Which consumers still force materialization?** Storage, return,
   capture, concatenation, UTF-8 encoding, any generic/dynamic call, any
   predicate with more than one parameter or any use besides the three
   supported shapes, and any consumer this analysis does not (yet)
   recognize.
7. **Does immediate literal comparison allocate?** No -- confirmed
   pre-existing (`view-predicate-*`) and newly for the classification
   argument case (`view-classify-*`).
8. **Does non-ASCII comparison allocate?** No -- `view-classify-astral-1`,
   `view-predicate-non-ascii-1`, and the Emailish corpus test itself (the
   dominant workload's own String is non-ASCII: café, 例え, テスト).
9. **Does sequential traversal still decode once?** Yes, and unaffected:
   this shape is not a `hir/traversal.tcl` loop at all (see above), and the
   new region ops each decode their one scalar exactly once.
10. **Can a virtual character survive a MayGc operation safely?** Yes --
    GC stress (collect before every allocation) across the full corpus and
    a dedicated repeated-predicate-scan test all produce correct results.
11. **How is the base String kept live?** By the same, unmodified
    per-register shadow-stack rooting every NIR register already has; no
    new liveness mechanism was added.
12. **Did removing allocations change may_gc summaries?** Not observably
    at the aggregate safepoint/root-candidate level for `refined-checks.ir`
    (see "Downstream compiler metrics" -- the call boundary to `char_at`'s
    region companion remains a conservative safepoint even though it no
    longer allocates).
13. **How many safepoints/root obligations disappeared downstream?** None
    in aggregate for this program (97/180/103/28, unchanged); 4 whole
    functions (`is_local_char`/`is_label_char` × 2 specializations)
    disappeared instead, via the compiler's existing reachability
    accounting.
14. **How many of the 13,600 remain?** Zero.
15. **Why would any survive?** N/A here; in general, a survivor would mean

## Primary acceptance case: family "A" and "B" independently

**Family A shape (`scan_local`/`scan_label`, argument to a user
predicate)**:

- source: `is_local_char(char_at(i))` / `is_label_char(char_at(i))`
  (`lib/web.tcl:86,94`)
- HIR: `call is_local_char [call char_at [ref i]]` -- a `block`-target
  call whose argument is itself a `block`-target call
- NIR before: `%5 = callenv 11 %4 %0` (materializing `char_at`, `op
  substr`) then `%6 = call 13 %5` (`is_local_char`, itself `guard`-free,
  `op strtclalnum`/five `op streq`)
- NIR after: `%5 %6 %7 = callenvmulti 12 %4 %0` (char_at's *existing*
  region companion, `op regioncheck`) then, inlined directly, `op
  strregiontclalnum %5 %6 %7` and up to five `op regioneq %5 %6 %7
  <literal>` -- no `call`/`callenv` to `char_at`'s materializing entry or
  to `is_local_char`/`is_label_char` at all
- allocation site: `func char_at`, `substr`, present (9,200/4,400
  combined before) → absent after
