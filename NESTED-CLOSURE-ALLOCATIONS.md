# Nested closure allocations: de-closure conversion

Milestone date: 22 September 2026. Prior source revision: `831288a`
("Stop tracking cached Go benchmark binaries"), the String-view allocation
milestone's own final commit. That milestone's own "what's next" answer
(#21-22 of `STRING-VIEW-ALLOCATIONS.md`) named `bench/refined-checks.ir`'s
remaining 7,205 Block (closure) allocations -- 413.0 KB of its 413.7 KB
total -- as the corpus's largest remaining allocation class by a wide
margin, and this milestone's mandate. Evidence generated by this milestone
is under `audit/nested-closure-allocations/`.

## Files changed

- `hir/blockescape.tcl` -- rewritten. The existing F1 pass (a locally-bound
  Block whose every reference is a direct call to one statically known
  instance, never captured by another Block, never recursive) is
  generalized to a bounded, single-region transitive fixpoint: a Block
  captured only by *sibling* Blocks that are themselves eligible, and a
  Block whose only self-reference is its own exact recursive call, no
  longer force materialization. New: `RefsAsCalls`, `SingleInstance`,
  `HasSelfCapture`, `FlattenBinding`, and a rewritten `Bindings` building a
  per-region candidate graph and its greatest fixpoint. The public API
  gains `captures` (a callee instance's flattened capture BindingId list)
  and now takes the already-computed `hir::stringregion` analysis as a
  third argument (to decline a candidate some caller asks for in "region"
  form -- see below). `virtual`/`wants` keep their old call signatures but
  are now keyed by BindingId alone, not `(InstanceId, BindingId)`.
- `native/lower.tcl` -- `Bind`'s virtualized-Block case becomes a pure
  no-op (like the pre-existing envless-in-statement-position case): a
  virtualized binding's captures are never evaluated or stored at bind
  time any more. `Call`'s dispatch (`VirtualBlockCall` renamed/rewritten as
  `FlattenedVirtualCall`) now resolves a callee's flattened captures fresh,
  in the calling function's own current scope, at every call site --
  external, sibling, or the callee's own recursive self-call -- and emits
  a `tail` loop backedge (never `tailenv`: an internal variant has no
  environment register) for a self-tail recursive call, with raw-parameter
  representation preserved. New: `CaptureRegsOf` (generalizes the old
  `CaptureValues` to an arbitrary BindingId list, not just one block
  expression's own captures). `captureLists`' construction gains an
  override step for every `wants`-flagged instance, from
  `hir::blockescape::captures` instead of the structural `CaptureList`.
  `program`'s analysis order changes: `stringregion` is now computed before
  `blockescape` (a dependency, not a coincidence -- see below).
- `tests/native-block-escape.test` -- 9 new tests (sibling capture,
  transitive three-deep capture chains, self-recursive and non-tail
  recursive virtualization, managed-capture GC stress through a sibling +
  self-tail chain, three mixed-kind captures, repeated creation by a
  recursive outer function); `blockescape-recursive-1` rewritten from "declines,
  documented limitation" to "virtualizes, zero Block allocation" (the
  capability this milestone adds).
- `audit/nested-closure-allocations/` -- generated evidence (HIR/NIR/VCode,
  allocation and root reports, corpus summary, census) for the before/on/off
  states.

No change to `core/`, `surface/`, `lib/web.bot`, `lib/web.tcl`, or any
`examples/stdlib/*.bot` source, and no change to `native/src/` (Rust): this
is purely a compiler-side representation change, using exactly the NIR ops
and runtime the String-view and prior Block-virtualization milestones
already had (the milestone's #10, #48, #66-68).

## Existing F1 semantics, before this milestone

`hir/blockescape.tcl`'s original `Bindings` (see its own header, reused
almost verbatim as this file's historical section) recognized a locally
bound Block `B` as *virtual* -- lowerable without ever calling
`rt_closure_new` -- only when, within `B`'s own enclosing region:

- `B` is bound once, non-duplicate, `local` kind, never in a trailing
  (implicit-return) position, never captured by a nested Block literal
  anywhere in the same region, and captures no forward-reference cell
  (`NeedsCell`).
- `B`'s own literal needs no "self" (`NeedsSelf`): no capture of `B`'s
  literal resolves, through `hir::aot::BoundBlock`, back to `B`'s own
  literal -- i.e. `B` is not recursive, directly or through a capture.
- Every reference to `B`, found in the *same* region's own top-level
  expressions, is the callee of a direct call with matching arity,
  resolved (`hir::specialize`'s own `calls` map) to one consistent callee
  instance.

Any other use -- and, critically, **any capture of `B` by another Block
literal in the same region, whether or not that other Block itself only
ever calls `B`** -- declined virtualization outright, unconditionally.
`native/lower.tcl`'s lowering side (`InternalFunction`, `VirtualBlockCall`,
`Bind`'s virtualized case) already supported exactly the representation
this milestone needed (a capture-explicit, `env=0` internal variant,
sharing the callee's canonical body) -- the limitation was entirely in
`hir/blockescape.tcl`'s *analysis*, not in what lowering could represent.
This is why the milestone's own #3 ("do not create parallel closure-escape
machinery if the existing pass can be generalized") was achievable: no new
NIR op, runtime call, or ABI shape was needed anywhere.

## Block runtime representation (unchanged, documented for scale)

`native/src/runtime/value.rs`'s `ClosureObj`:

```
struct ClosureObj {
    hdr: Header,      // 8 bytes: kind, marked, is_static, padding
    func: u32,         // 4 bytes: NIR function id
    arity: u32,        // 4 bytes
    code: usize,        // 8 bytes: JIT code pointer
    ncaps: usize,       // 8 bytes
    caps: *mut Value,   // 8 bytes: boxed capture array pointer
}
```

40 bytes fixed, plus 8 bytes per capture (a separate `Box<[Value]>`
allocation the heap's own byte-accounting folds into the same site,
`rt_closure_new`'s `n as usize * 8`). `char_at`'s own closure (one
capture, `v`) is 48 bytes -- exactly what every surviving allocation site
below reports. Nothing about this layout changed; this milestone's whole
effect is to stop calling `rt_closure_new` for five of the six dominant
closures, not to redesign what it produces for the sixth.

## Taxonomy: why each of the 7,200 recurrent allocations survived F1

Every one of the six families falls into taxonomy classes **D** (captured
by another closure) and/or **G** (recursive/self-tail closure
representation) from the milestone's own list:

- **char_at**: class **D** only. Not recursive. Captured -- as a *value*,
  per HIR's structural capture propagation -- by `scan_local`,
  `scan_label`, `scan_alpha`, and `domain_loop`'s own Block literals (each
  calls `char_at(i)` from inside its own nested body); also directly called
  from `Emailish?`'s own top-level body. F1's blanket
  `dict exists $captured $b` check declined it the moment *any* nested
  Block literal in the region captured it, without asking whether that
  capturer's own use was itself just a call.
- **scan_local**: class **G** only (not captured by any sibling). Its only
  problematic reference is its own recursive call
  (`scan_local(i+1)`, self-tail) -- F1's `NeedsSelf` declined any Block
  whose literal captures itself, unconditionally.
- **scan_label**, **scan_alpha**: both **D and G** -- self-recursive
  *and* captured by `domain_loop` / `tld_ok` respectively.
- **tld_ok**: class **D** only -- not recursive, but captured by
  `domain_loop`'s own body (`tld_ok(i2)`).
- **domain_loop**: class **G** only -- self-recursive (`domain_loop(i2)`);
  not captured by any sibling (only `Emailish?`'s own trailing body and
  itself call it).

No allocation among the 7,200 is class **A** (identity genuinely
observable), **B** (stored in a container), **C** (returned), **E**
(passed as an ordinary value to unknown code), or **H**; every one is,
per the milestone's own central question, "only an implementation vehicle
for transporting a statically known function target plus captured values
to an exact call" -- for five of the six, all the way through. The sixth
(`char_at`) turns out to need one further, narrower reason to stay
materialized -- see "What survives, and why" below.

## The transformation: capture lifting as a bounded, single-region fixpoint

`hir/blockescape.tcl`'s new `Bindings` builds, per used specialize
instance (one region), a **candidate graph**: every local, non-trailing,
non-cell-capturing Block bind in that region is a node (the same
structural filter F1 always used, minus the automatic self/captured
exclusions). For candidate `B` (literal `L`, arity `N`):

1. **Self references** -- every `ref` to `B` found inside `L`'s own body
   (`RefsAsCalls`) must be exactly an `N`-argument call resolved to `L`'s
   own single used instance (`SingleInstance`; see its own comment for why
   a Block literal routinely has a second, always-present but call-free
   *generic* instance that must not by itself disqualify it). If `L`
   structurally captures itself but no such direct self-call is found
   (the reference is nested inside some further closure of `L`'s own --
   out of this milestone's scope), decline conservatively.
2. **External references** -- every `ref` to `B` found directly in the
   enclosing region's own top-level expressions must likewise be exactly
   a matching-arity call to the same target instance.
3. **Sibling references** -- for every *other* candidate `C` in the same
   region whose own literal structurally captures `B` (HIR's own
   `captures` field, which -- like any lexical closure conversion --
   already threads a free variable through every enclosing scope between
   its use and its binding, so this catches `char_at`'s capture by
   `scan_local` etc. even though the actual *use* is inside `scan_local`'s
   own nested body, a different region than the top-level one), every
   reference to `B` found directly in `C`'s own body must be exactly a
   matching-arity call to the same target -- and `C` itself must be
   eligible. An opaque capturer (a Block literal in the region that
   captures `B` but is not itself a recognized candidate -- returned,
   stored, or anonymous) disqualifies `B` outright. If `B` is
   *structurally* captured by `C` but no direct reference to it is found
   in `C`'s own body at all, the actual use must be nested deeper (this
   analysis does not look that far) -- declined conservatively rather than
   risked.
4. **hir::stringregion interaction** -- `B`'s target instance must not be
   one `hir::stringregion.tcl`'s own analysis already decided some caller
   asks for in *region* form (see below); if it is, decline.
5. A candidate with **no** reference found by (1)-(3) at all (unreachable,
   or reachable only through some other mechanism this analysis does not
   model, such as the native-to-module bridge) also declines: absence of a
   *disqualifying* use is not itself proof every real use is a call.

This is a **greatest fixpoint**: start with every structurally-simple
candidate tentatively eligible, remove any that fails (1)-(5) (declining a
sibling capturer removes its own dependents in the next pass), repeat
until stable. For `refined-checks.ir`'s single region (`Emailish?`'s own
body), the graph is small (6 nodes, 1 removal after the `stringregion`
check for `char_at`) and converges in two passes.

**Flattened captures** (`FlattenBinding`): for each eligible `B`, its
*structural* captures are walked once; a captured binding that is itself
an eligible candidate is replaced, recursively, by *its own* flattened
list (capture lifting propagated through the closed call chain -- the
milestone's #7/#20); a self-reference or an envless (fnvalue) reference
contributes nothing; everything else (a genuine external value -- `v`,
`n`, or, for `char_at`, a real captured Block since it itself declines) is
a terminal capture, deduplicated in first-occurrence order (deterministic,
since every source list is). For `refined-checks.ir`: `scan_local`,
`scan_label`, `scan_alpha`, `tld_ok`, and `domain_loop` all flatten to
exactly `[n, char_at]` -- `char_at` itself stays a **real, terminal**
capture (a genuine Block value), because `char_at` did not qualify (see
below); had `char_at` also qualified, this would have flattened further
to `[n, v]`.

**Lowering** (`native/lower.tcl`): a virtualized binding's `bind`
statement becomes a pure no-op -- captures are never evaluated or stored
at bind time. Every reference to it, wherever it occurs (the enclosing
region's own body, a sibling candidate's own body, or the callee's own
recursive self-call), is intercepted before the callee expression is ever
evaluated as a value (`Call`'s new early dispatch, keyed by BindingId
alone via `hir::blockescape::virtual`) and resolves the target's flattened
captures **fresh**, in the calling function's own current scope
(`CaptureRegsOf`). This is sound by construction: a candidate's flattened
capture list is, transitively, always a subset of whatever its own
callers' flattened capture lists (or top-level bindings) already contain,
so every register `CaptureRegsOf` asks `Access` for is already in scope.
A self-tail recursive call becomes a `tail` loop backedge (never
`tailenv`: an internal variant has no environment register at all) with
its own capture registers re-passed as ordinary loop-carried parameters,
raw-parameter representation preserved exactly as the pre-existing
self-tail mechanism already provides for a materialized closure. A
non-tail recursive or sibling call is an ordinary `call` to the callee's
own internal variant.

## What survives, and why: `char_at`

`char_at` is the one dominant family this milestone does **not**
eliminate. Its external and sibling references are *not* all ordinary
tagged calls: `Emailish?`'s own trailing body compares `char_at(localEnd)
== "@"` directly, and `domain_loop`'s body compares `char_at(labelEnd) ==
"."` -- both StringRegion "Class A" immediate-`==` consumers
(`STRING-VIEW-ALLOCATIONS.md`), and every `is_local_char(char_at(i))` /
`is_tcl_alpha(char_at(i))` call (from `scan_local`/`scan_label`/
`scan_alpha`) is *also* lowered by asking `char_at`'s call for a *region*
result (`Call`'s `wantRegion` path, `native/lower.tcl`'s "String regions"
section), reaching `char_at`'s **canonical, closure-taking region
companion** via `callenvmulti` -- which needs a real captured-environment
register, not a capture-explicit internal variant with none. Virtualizing
`char_at` regardless (an early implementation attempt, kept only in this
report as the failure it produced) crashes lowering outright: the no-op
`Bind` leaves nothing for `ModuleBridgeBinding`-style or `wantRegion`-path
callee evaluation to find. `hir::blockescape.tcl` now asks
`hir::stringregion::wants` directly (a new required third argument, and
the reason `program`'s analysis order changes to compute `stringregion`
first) and declines any candidate a region-form caller already claims --
precisely and only for those, not a blanket exclusion. Composing the two
optimizations further (an *internal*, capture-explicit region companion)
is real, identified scope -- deliberately not attempted here (the
milestone's #77 "smallest sufficient scope", #10 "do not build a second
unrelated ABI").

Because `char_at` still materializes, its five callers gracefully degrade
rather than lose their own optimization: `FlattenBinding` simply keeps
`char_at`'s own binding as an ordinary terminal capture (a real Block
value) in their flattened lists, exactly as any other captured value would
be -- `scan_local` etc. still allocate zero Blocks of their own; they just
each receive `char_at`'s one real, already-materialized closure as one of
their own capture parameters, precisely like `n`.

## Register pressure

Flattening turns what was one environment pointer (`env=1`, one NIR
register) into up to two ordinary parameters (`n`, `char_at`) threaded
through every virtualized function's own signature and every recursive
loop backedge. `refined-checks.ir`'s own shadow-slot count above (109 vs
103, +5.8%) is the concrete, measured cost of this for a capture width of
2 -- small next to the 24-safepoint, 1,952-byte, 6,004-allocation win, and
not evidence a bounded-capture-count profitability policy (the milestone's
#74) is needed for this workload. No such policy was added; this remains
an evidence-backed, not a preemptive, decision (#76-78).

analysis does not model the module bridge as a call at all.

## Correctness, GC stress, and regression testing

No new flag: this milestone extends the existing `-block-escape-opt 0` /

## Answers to the milestone's 28 questions

1. **Exact sources of the 7,205 Block allocations?** Two families:
   `char_at`/`scan_local`/`scan_label`/`scan_alpha`/`tld_ok`/`domain_loop`
   (6 sites × 2 literal-String instances = 7,200, the census table above)
   and 5 non-recurrent `web.bot`/`uriEscape` module-startup closures.
2. **Which sites account for the 7,200?** All twelve, in equal measure --
   see the census table; no site dominates the other eleven.
3. **Why did F1 miss them?** Two blanket, unconditional exclusions:
   captured by another Block literal in the same region (regardless of how
   that capturer used it), and self-recursion (`NeedsSelf`), neither of
   which asked whether the actual use was itself just an exact call.
4. **Which genuinely escape?** None of the 7,200 (see the taxonomy table:
   every one is class D and/or G, never A/B/C/E/H). The 5 module-startup
   closures also do not escape in the ordinary sense, but 1 of them
   (`web::uri_escape_text` itself) is reached by a mechanism (the
   native-to-module bridge) this analysis does not model as a call, so it
   is conservatively left materialized.
5. **Which exist only to transport captures to exact calls?** Five of the
   six families, fully: `scan_local`, `scan_label`, `scan_alpha`,
   `tld_ok`, `domain_loop`. The sixth, `char_at`, also transports captures
   to exact calls for *most* of its uses, but two of its callers ask for
   its result in StringRegion "region" form, which needs a real
   environment register.
6. **What representation replaces eligible heap closures?** A
   capture-explicit internal variant (`env=0`), exactly
   `hir/blockescape.tcl`'s pre-existing F1 mechanism -- generalized only in
   *which* candidates qualify and in *where* their captures are resolved
   (fresh, per call site, rather than stored once at bind time).
7. **Hidden parameters, field-expanded data, or something else?** Hidden
   direct parameters: each flattened capture is one ordinary trailing NIR
   parameter of the callee's internal variant. No field expansion was
   needed for this workload (`char_at` and `n` are each already scalar).
8. **How are nested closure captures handled?** `FlattenBinding`
   recursively substitutes an eligible captured candidate's own flattened
   capture list in its place; a self-reference and an envless reference
   both contribute nothing; a genuinely terminal (non-candidate, or
   ineligible) capture passes through as an ordinary value -- gracefully
   degrading to a real captured Block when needed (`char_at`, for its five
   callers).
9. **Can A remain virtual when nonescaping B captures it?** Yes -- this is
   the central mechanism (`scan_local` etc. capturing `char_at`, or, in
   the general case, any sibling-capture chain whose every use is an exact
   call).
10. **What happens when B escapes?** A captures it (an opaque or
    escaping capturer) declines: `capturedBy`'s check requires every
    capturer to itself be a recognized, eligible candidate whose own use is
    a pure call (`blockescape-sibling-escaping-1`).
11. **Interaction with self recursion?** A candidate's own self-reference,
    proven to be nothing but its own exact recursive call, needs no
    "self" (running-closure identity) value at all: the recursive call
    resolves as a direct call to the same internal variant, passing the
    same capture registers back.
12. **Interaction with self-tail-to-loop lowering?** Preserved and
    extended: a self-tail recursive virtualized call becomes a `tail`
    loop backedge (not `tailenv`), re-passing its own flattened captures
    as ordinary loop-carried parameters each iteration, with raw-parameter
    representation for range-proven Int parameters unchanged.
13. **Are any function bodies inlined?** No. Every lifted call remains an
    ordinary direct function call (to an internal variant); no callee
    body is copied into any caller.
14. **Are canonical materialized closure entries still available?** Yes,
    unconditionally emitted for every instance regardless of whether any
    caller ever uses it virtually (`Function`, unchanged) -- for
    `refined-checks.ir` specifically, the five families' own canonical
    entries became *unreachable* (every actual caller is now flattened-
    virtual) and were dropped by the compiler's pre-existing reachability
    accounting, not by anything this milestone added.
15. **How are managed captures kept alive across MayGc calls?** Exactly as
    any other live NIR register: codegen's existing per-register
    shadow-stack rooting, unmodified (`blockescape-gc-stress-2`).
16. **Did GC stress find any lifetime/rooting bug?** No.
17. **Did removing closure allocation improve `may_gc` summaries?** Not
    for `refined-checks.ir`: `char_at` still allocates, so its five
    callers' `may_gc=true` is unchanged (correctly conservative).
18. **Safepoints/root obligations that disappeared?** 24 safepoints, 27
    root candidates, 7 entry-zero slots (summed over all 27 functions);
    shadow slots rose slightly (+6) -- see "Register pressure."
19. **How many of the 7,200 remain?** 1,200 (`char_at`'s own two sites);
    6,000 are eliminated.
20. **Why do survivors remain?** `char_at`'s result is asked for in
    StringRegion "region" form by two of its call sites, which reaches its
    canonical, closure-taking region companion via `callenvmulti` --
    needing a real environment register this milestone's internal
    variants do not have. Composing the two optimizations is identified,
    separately-scoped future work.
21. **Did String allocation stay at ~9 objects?** Yes, unchanged (9 → 9).
22. **Did lifted capture passing create problematic register/frame
    pressure?** A modest, measured increase (+6 shadow slots, +5.8%) for
    this workload's 2-capture width -- not problematic next to the win; no
    profitability policy was added.
23. **Did machine-code size increase or decrease?** Decreased: 20,846 →
    18,894 bytes (-9.4%).
24. **`refined-checks` runtime now?** ~460-600 µs (Cranelift, best-of-5,
    isolated single-program runs; noisier when benchmarked alongside other
    programs in one invocation due to shared sandbox contention), down
    from 814.54 µs at the String-view milestone's own baseline.
25. **Does the optimization apply anywhere else in the corpus?** Within
    `refined-checks.ir`, yes, to `uriEscape`'s own four nested helpers
    (a byproduct); across the rest of the 13-program corpus, no other
    program defines a locally recursive or sibling-captured Block, so no
    other program's allocation profile changes.
26. **Dominant remaining allocation class/site?** Block, still -- 1,201 of
    1,215 total objects (57.6 KB of 58.3 KB), now entirely `char_at`'s own
    1,200-allocation pair plus the 1 module-startup closure. No other
    class comes close.
27. **Another Block milestone justified, or return to String/Bytes?**
    `char_at`'s own survival is a single, well-understood, narrow-scope
    gap (composing capture lifting with StringRegion's region-companion
    mechanism) -- a bounded second milestone specifically for it is
    justifiable and would plausibly close the corpus's entire remaining
    Block allocation count for this program to near zero (~1 -- the
    module-startup closure), matching outcome **B** of the milestone's
    own #101 more than **A** (nearly all Blocks did disappear, but one
    well-understood shape remains) or **C** (nothing here is a genuine,
    permanent semantic escape).
28. **Next milestone the new profile supports?** Two concrete, evidence-
    backed candidates, both smaller in scope than this one: (a) an
    internal (capture-explicit) StringRegion companion for `char_at`,
    closing its own remaining 1,200-allocation pair; (b) `uriEscape`'s own
    `encode_utf8`-then-List intermediate and `esc_bytes`/`esc_from`'s
    repeated `concat` (String-view's own #22 answer, still unaddressed,
    still small relative to everything measured here). Not implemented,
    per the brief.
