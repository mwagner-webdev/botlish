# RAVEN-BINDINGS.md

Botlish bindings for [Raven](https://oscar-soirey.github.io/Raven/), a GUI
library written in C11, and a wrapper library over them. This document
also reports what Botlish lacks for such a library.

Three things were built:

* **The generated binding.** `tools/c-bindgen.tcl` turns Raven's public
  headers into ordinary Botlish modules (`raven::core`, `raven::window`,
  `raven::controls`, ...). It binds 921 of 923 API names, and all 27 of
  Raven's complete records become layouts. The output is committed for
  Linux x86-64 and AArch64 (`generated/c/raven/TARGET/`).
* **The wrapper package.** `packages/raven` is the module `raven`: windows,
  panels and controls as nominal handles, the frame loop, events, themes,
  actions, timers and synthetic input. It also includes a small C *event
  bridge*. Raven reports every event through a C callback, and no Botlish
  function can be a C callback. The bridge records what Raven reports, and
  the program reads those records after each frame.
* **The example, tests and CI.** `examples/raven/` is the counter program
  from Raven's guide, written in Botlish. The tests run headless on both
  native backends. They also run on a real X11 window that Raven's Vulkan
  renderer draws, under Xvfb with Mesa's software Vulkan driver.

**Missing language features (section 7).** The one feature this library
needs and Botlish does not have is **C callbacks into Botlish**
(`FnPtr` values made from Botlish functions). 74 of Raven's 921 functions
take a callback. The event bridge covers the events: anything Raven only
*reports*. It cannot cover a callback whose answer depends on the
program's own code, such as custom-painted widgets, virtual lists, data
providers, an event handler that decides whether to consume an event, a
drop target that decides whether to accept, worker tasks or a custom
allocator.

Three smaller gaps cost wrapper code but block nothing:

* out-parameters to C ints and floats (41 functions);
* reading a C string or buffer whose length is known only at run time
  (69 functions return a `const char *`);
* C floats that make every call fallible (155 functions); a caller can
  now choose the raw C value instead, function by function
  (RAW-C-FLOAT-FFI-MILESTONE-1.md, section 7.4).

## 2. Raven

Raven (github.com/oscar-soirey/Raven, Apache License 2.0) is a
retained-mode GUI library for editors and tools. It has native windows
(Win32, X11, Cocoa), a Vulkan renderer, a Slate-like layout model,
interfaces described in XML or built in code, and about 40 widget types
(including a code editor, docking, a node graph and a timeline). It is
built with CMake and needs only libX11's headers on Linux. Vulkan is loaded
at run time.

The parts of its API that matter for a binding:

* **Every object is a `Rid`, a `uint32_t` handle** with a generation
  counter. Raven checks a handle on every call, so a deleted object's handle
  is reported, never a crash. There are no object pointers.
* **Booleans are `int`, colors are four `float`s, and strings are UTF-8,
  "always copied by the library".** A returned string stays valid until
  the next call that returns one of its kind.
* **Raven has no loop of its own.** The application asks for one frame at a
  time (`Rdraw_frame`, or `Rwait_frame(timeout)`, which sleeps until
  something happens).
* **Everything that happens is reported by calling a C function** that the
  application registered: control callbacks, actions, a window's close and
  resize, timers, errors, raw input, drop targets, paint and measure
  callbacks of custom widgets, item providers of virtual lists, worker
  tasks.
* **Headless runs are built in.** `R_BACKEND_NULL` with `headless = 1`
  creates no OS window and draws nothing. `Rwindow_inject_*` gives
  synthetic input.

`tests/cffi/raven.tcl` builds the pinned release as the shared
`libraven.so` in Botlish's cache, never in the repository. By default it
builds the headless configuration (`-DRAVEN_PLATFORM=null
-DRAVEN_BACKEND_VULKAN=OFF`), which needs no X11 package and no download.
`BOTLISH_RAVEN_CMAKE_FLAGS=""` builds the desktop configuration (X11 and
Vulkan; the Vulkan headers are downloaded at configuration) into a
directory of its own. Each build takes about 10 s.

## 3. The generated binding

### The profile

`tools/c-bindgen/profiles/raven.tcl` describes the binding:

* the entry header `Raven.h`, which includes the 20 `raven/raven_*.h`
  headers;
* modules named by stripping the prefix `raven_` (so `raven_window.h`
  becomes `raven::window`);
* one library, `raven`;
* the manual contracts;
* the representations: the five functions whose C floats and doubles the
  binding writes raw (RAW-C-FLOAT-FFI-MILESTONE-1.md, section 7.4).

The contracts follow from Raven's documented string convention. The
convention is stated once in `raven_core.h` ("strings are UTF-8 and always
copied by the library"), so every `const char *` parameter is read during
the call and never kept: `read noescape`. The profile states this for each
of the 172 such parameters, as 30 groups keyed by parameter name. Each
group lists its functions explicitly. The generator never infers a fact
from a C type (C-BINDGEN.md, "Contracts"), so writing these contracts down
is the binding author's job. Every other pointer parameter (out-parameters,
descriptors, user data) stays unknown.

No Raven function hits any of these blockers:

* aggregates passed by value;
* variadic arguments;
* `long double` or C `_Bool`;
* explicit calling conventions.

C `float` and `double` are bound (C-FLOAT-FFI-MILESTONE-1.md); 155
functions use one. Raven's `int` booleans are plain `std::ffi::c::Int`,
and its enums are the C types the compiler gives them (`unsigned int`).
`Rid` is an ABI alias of `std::ffi::c::UInt`.

A program over the binding alone is ordinary: it needs no `direct module`.
Its calls take handles, numbers and strings, and the strings are lent as
bytes under the profile's `read noescape`
(`examples/ffi/bindgen/raven/demo.bot`). By contrast, a call that hands
Raven a pointer it says nothing about (`Rinit_ex`'s descriptor, an
out-parameter) is direct authority (DIRECT-MODULES.md).

### Symbols and builds

`raven_vulkan.h` is part of `Raven.h` in every configuration, but its 14
functions exist only in a build with the Vulkan backend. A program that
calls one links against a Vulkan build only. Every other function is
exported by every build (`cb-raven-symbols` checks the headless build's
exact gap, and that a Vulkan build has none). The header's
`RAVEN_VERSION_*` constants say 0.1.0, while the v0.1.3 library's
`Rget_version()` says "0.1.3". The binding states what the header says.

### The toolchain

Committed bindings record the clang that generated them, and the
repository's rule is to generate them with the pinned clang 21.1.8 of
Ubuntu 26.04 (C-BINDGEN-UBUNTU-26.04-HANDOFF.md). This work ran on an
Ubuntu 24.04 container (clang 18), so the binding was generated in an
Ubuntu 26.04 chroot. The chroot was made with debootstrap, and
`.devcontainer/setup-c-toolchain.sh`'s pinned clang, LLVM and arm64 cross C
library were installed into it, with the repository bind-mounted. The same
chroot reproduces the committed fixture byte for byte. With clang 18,
`cb-raven-current` passes too: it compares every byte but the recorded
provenance.

## 4. The package

```
APP/.bot_modules/raven/          tools/raven-package.tcl install APP
    raven.bot                    the module raven (packages/raven/raven.bot)
    raven/core.bot ...           the GENERATED binding of the host's target, staged
    native/raven_bridge.c        the event bridge's source
    native/libraven_bridge.a     built by the install (cc -Werror, the pinned Raven's headers)
```

The wrapper and the binding are one package with one root namespace. The
wrapper is `raven`. The binding's modules are `raven::core`,
`raven::window` and so on, available to the application for anything the
wrapper leaves out. Each handle's `id` field is the `Rid` those functions
take:

```botlish
raven::controls::Rlabel_set_markdown(label.id, 1)
```

The bridge is linked from the package instance
(`extern c library "raven_bridge" static at "native/libraven_bridge.a"`).
Raven itself is linked by `-L` and found at run time by `LD_LIBRARY_PATH`.

```botlish
import raven

with context raven::create()

fn main(context ui: raven::Ui) -> int errors raven::RavenFailed, NonFiniteFloat:
    raven::start(raven::desktop())
    w = raven::window("Hello", 420, 220)
    quit = raven::button("Quit")
    w.set_content(raven::vbox().add(raven::label("Hello from Botlish")).add(quit))
    count = loop_until_quit(quit, 0)        # a wait_frame loop over raven::events()
    raven::stop()
    count
```

The surface:

* **Handles.** `Window`, `Widget` and `Timer` are each one `Rid` under a
  nominal type. A widget can never be passed where a window is meant,
  something the binding's plain `UInt` handles allow.
* **Lifetime, under the context `Ui`.**
  * `start(options)` writes the `RInitDesc` layout into native memory and
    calls `Rinit_ex`. The options are `desktop()` or `headless()`.
  * `stop()`.
  * `running?()`.
  * `last_error()`, which reads Raven's error through `Rerror_get_last`'s
    out-parameters.
  * `size(window)`, `rect(widget)` and `capture(window)`, which read
    out-parameters or a frame.
* **Frames.** `draw_frame()`, `wait_frame(timeout)`, `quit(code)`,
  `exit_code()`.
* **Events.** `events()` returns every event recorded since the last call,
  oldest first. An `Event` has a kind (`Clicked`, `Toggled`,
  `ValueChanged`, `TextChanged`, `TextCommitted`, `Selected`, `Action`,
  `CloseRequested`, `Resized`, `TimerElapsed`, `Error`), a source handle,
  two ints, a number and a text. `from?(event, widget)` tells which widget
  an event came from.
* **Building.**
  * Windows: `window`, `window_from_xml`, `find`, `set_content`,
    `set_title`, `keep_open`, `request_close`, `destroy_window`.
  * Panels: `vbox`, `hbox`, `add` (chainable), `set_spacing`,
    `set_padding`.
  * Controls: `label`, `button`, `checkbox`, `slider`, `spin_box`,
    `text_input`, `combo_box`, with their getters and setters. A slider's
    and a spin box's value come both ways: raw (`slider_raw_value`,
    `spin_box_raw_value`: the C float or double, every bit) and admitted
    (`slider_value`, `spin_box_value`: the explicit admission to a Float64,
    NonFiniteFloat for a NaN or an infinity), with raw setters beside the
    finite ones (RAW-C-FLOAT-FFI-MILESTONE-1.md).
  * Others: `apply_theme`, `bind_action`, `set_action`, `fire_action`,
    `timer` and `cancel`.
* **Synthetic input.** `inject_click`, `click(window, widget)` (which
  clicks at the middle of where the last frame laid the widget out),
  `inject_text`, `inject_key`.

**Authority.** Most of the wrapper needs no authority, because handles,
numbers and strings are ordinary arguments. Only native memory needs it:
the `RInitDesc` descriptor and one cell per out-parameter, allocated with
the C library's `calloc` and read and written through private layouts.
Every function that touches native memory requires `Ui`, the context this
module declares. The context owns the pointers in a `MutableVector`
(CONTEXT-OWNED-AFFINE-STATE-MILESTONE-1.md) and reaches them where they
are stored (`ui.open.element(0).width`). This is the same airlock that
Icy Tower's `sdl.bot` uses. The program installs the context, and nothing
above the module is direct. `raven-authority` checks both sides: a
top-level call of the raw `Rinit_ex` is DIRECT, and a `direct module` on
the example is STALE-DIRECT-MODULE.

**`nomethod`.** The functions that make something from a text, number or
list (`window`, `label`, `button`, ... `bind_action`, `fire_action`) are
`nomethod`. Without it, METHOD-ELIGIBLE would suggest
`"Sizes".window(420, 220)`.

## 5. The event bridge

`packages/raven/native/raven_bridge.c` is the only C code the package
adds. It has one callback per Raven callback signature the wrapper uses:

* `br_clicked`, for buttons and menu items;
* `br_toggled`, for checkboxes;
* `br_slider` and `br_spin_box`;
* `br_text_changed` and `br_text_committed`;
* `br_selected` and `br_activated`;
* `br_action`, which handles both `Raction_bind` and the default action
  handler;
* `br_close` and `br_resized`;
* `br_timer` and `br_error`.

Each callback copies its arguments into a record: kind, source, two ints,
a double, and a `malloc`'d copy of any text. Records go into a growing
ring buffer, and none is overwritten. A record that memory cannot hold is
counted (`botlish_raven_lost`). The program registers what it wants to
hear about (`botlish_raven_watch_button(Rid)`, ...), which the wrapper does
when it makes a control. It takes records one at a time
(`botlish_raven_next`, and scalar getters for the current record).

The rules it keeps:

* **It never calls Botlish.** No Botlish code runs inside a Raven frame.
  This is the same rule as the event loop's native integration ABI
  (EVENT-LOOP-MILESTONE-1.md).
* **It never keeps a pointer that Raven gave it past the callback.** Text
  is copied.
* **It decides nothing for the program but the answer a callback must give
  at once.** A close request is answered by the policy the program stated
  when it watched the window (`keep_open`). The record then says what was
  answered.
* **It is ABI-versioned.** `start` checks `botlish_raven_bridge_abi() == 1`
  before anything else (`raven-bridge-abi`).
* **The queue is locked.** All callbacks run on the UI thread, except the
  error callback, which Raven calls on the thread that raised the error.

Text reaches Botlish through `botlish_raven_text_length` and
`botlish_raven_text_copy`, which copies into a `MutableBytes` lent
writable for the call (C-POINTER-BORROWING.md). The same path reads every
string Raven returns (`label_text`, `input_text`, `version`, error
details). A captured frame of 4·w·h bytes comes back through
`botlish_raven_bytes_copy` (section 7.3 explains why these copies are C).

What it records, end to end, from one headless run (`raven-events`):

```
Action go 0 0 0 [hello.clicked]          an XML button's OnClicked, from the button
Toggled checkbox 1 0 0 []
TextChanged input 0 0 0 [h]               ... [he], [hey]: every edit
TextCommitted input 0 0 0 [hey]           Enter
CloseRequested window 0 0 0 []            kept open: value 0, the window still open
Error none 113 130 0 [Rwidget_destroy: invalid widget handle 0x00003039]
```

Raven reports what the user does, not what the program does: a combo
box's selection or a slider's value set by the program is no event.

## 6. The example

`examples/raven/counter.bot` is the "any language" program from Raven's
guide (section 10). The interface is Raven's XML: a label and two buttons
whose clicks fire `hello.clicked` and `app.quit`. The code is a frame loop
that handles the events after each frame:

```botlish
fn run(window: raven::Window, count: int) -> int errors NonFiniteFloat:
    if not raven::wait_frame(-1.0):
        return count
    window.run(window.step(count))
```

`run` is self-tail-recursive, which the native backends compile to a loop.
`step` folds `raven::events()` into the count and sets the label. There
are two entries:

* `main.bot` starts Raven with its defaults and runs until the window
  closes.
* `headless.bot` starts it headless and injects three clicks of
  "Click me" and one of "Quit". Its value is
  `["3", "3 clicks", "false", "0"]`.

```sh
tclsh9.0 tests/cffi/raven.tcl                       # headless libraven.so (DIR)
tclsh9.0 tools/raven-package.tcl install examples/raven
LD_LIBRARY_PATH=DIR tclsh9.0 main.tcl -backend cranelift -L DIR examples/raven/headless.bot
```

## 7. Missing language features

These are ranked by what they cost the binding. Each was met while writing
the wrapper; the compiler's diagnostics are quoted where it gave one.

### 7.1 Callbacks into Botlish (blocking)

C cannot call Botlish. `std::ffi::c::FnPtr[F]` types a C function pointer,
but no Botlish function can be one: C-FFI.md, "Not here" ("Callbacks
(Botlish code called from C) ... calling an `FnPtr`"). C-ABI-TYPES.md
lists what the feature would take: an `FnPtr` value made from a top-level,
non-capturing function with a C signature (its address and a C-ABI entry
trampoline), and no Botlish error or `yield` crossing a C frame. `exported
c fn` exists, but only for native libraries, which C hosts call; a
program cannot hand one to a C library it calls.

74 of Raven's 921 functions take a callback (57 callback typedefs). The
bridge (section 5) covers every callback that only *reports*: clicks,
changes, text, selection, actions, close and resize, timers, errors. The
program reads these after the frame, which is how a Botlish program would
structure a GUI loop anyway. It does not cover callbacks whose **answer
depends on the program's code**, which Raven needs while it is inside a
frame:

| Raven needs, synchronously | for | without callbacks |
|---|---|---|
| `RPaintCallback`, `RMeasureCallback` | custom widgets (`R_WIDGET_CUSTOM`): painting with `Rdraw_rect`/`Rdraw_text`, springs, measuring | impossible: drawing happens inside the paint |
| `RListItemTextCallback`, `RTileItemCallback`, `RTileDragDataCallback` | virtual lists and tile views of any size: Raven asks for the rows it draws | only non-virtual lists (`Rlist_view_add_item` for every row) |
| `RWidgetEventCallback`, `RWindowEventHook` return values | raw input that consumes an event (`return R_TRUE`) or lets it bubble | could be recorded, but the consume/bubble decision must be fixed in C in advance |
| `RDropCallback` return value | accepting or refusing a drop by its type or content | same: a fixed policy at most |
| `RWindowCloseCallback` return value | "Discard the changes?" decided when the close is asked | the bridge's fixed policy (`keep_open`) and a CloseRequested event: the program then closes the window itself or not |
| `RTaskCallback`, `RParallelRangeCallback` | `Rtask_run_async`, `Rparallel_for`, `Rtask_post` | none: Botlish programs have no threads of their own, so code on Raven's workers would be C |
| `RAllocator`, `RViewportDrawCallback`, `RVulkanQueueLockCallback` | the application's allocator, its own rendering inside a viewport | C only |

The last three rows also need code that runs on another thread. For the
others, the feature is the C-ABI-TYPES.md item above plus re-entrancy:
Botlish code called from C while a Botlish frame is below it on the stack
(the program called `Rdraw_frame`). This needs the collector's stack walk
across the C frames in between, which native libraries already bound
(`Vm::stack_ceiling`, NATIVE-LIBRARY-MILESTONE-1.md), and the rule that no
Botlish error unwinds through Raven.

### 7.2 Out-parameters (costly, worked around)

41 functions return results through pointers to C ints, floats or
pointers, for example:

```c
void Rwindow_get_size(Rid, int* w, int* h)
void Rwidget_get_rect(Rid, float*, float*, float*, float*)
RError Rerror_get_last(const char**, RSeverity*)
uint8_t* Rwindow_capture(Rid, int*, int*)
```

Botlish has no way to give C the address of a Botlish value. Byte storage
can be lent only to a byte-sized pointee (C-POINTER-BORROWING.md). There
is also no pointer offset, so one allocation cannot hold several cells.
The wrapper therefore allocates one native cell per out-parameter, nine in
all: the descriptor, two ints, four floats, a `const char *` and a
severity. It also declares a private layout per cell type and reads each
cell with `std::binary::native::view`. Because the cells are native memory
behind pointers, every function that uses them requires the context
(section 4). The compiler steered this well; its messages named the fix
each time:

```
field "width" of `scratch` is affine (...): reading it would make a second owner ...
(consume the struct with a destructuring instead: "{width} = scratch")
`ui.open.element(...)` is an affine raven::Scratch that the installed context raven::Ui owns:
binding it to a name would copy it out ... Reach it where it is stored -- observe it (a C call, null?, clone) ...
```

What would remove the cost: an out-parameter form of the foreign-call
contract, matching `write noescape` for bytes, for scalar pointees. A
`write noescape` `Ptr[Int]` parameter would give its value back in the
call's result, as a written `MutableBytes` already is
(`{result: R, NAME: ...}`).

### 7.3 C memory of a size known at run time (worked around in C)

69 functions return a `const char *`. A NUL-terminated string has no size
Botlish knows. Native views read a layout, whose size is fixed when the
program is compiled; the standard library reads `readdir`'s names through
a 1024-byte array field and the length the record stores, which works
only because that record has a maximum. Raven's strings (a text editor's
whole document, for example) have none, and neither has a captured frame
(4·w·h bytes). The bridge therefore copies such memory into a lent
`MutableBytes`. That is two small C functions, but every C library with
strings will need the same pair. What would remove it: a standard
operation that copies N bytes (or a NUL-terminated string) from a
`Ptr[Char]`/`Ptr[UChar]` the program already has authority to read into
new Botlish `Bytes`. That operation is a read of native memory, so it is
direct.

### 7.4 C floats make calls fallible

A Float64 outside binary32's range cannot be narrowed to a C float, and a
non-finite float that C returns cannot be a Float64. Both are
`NonFiniteFloat`, checked before C runs (C-FLOAT-FFI-MILESTONE-1.md).
That is correct, but in a GUI library whose coordinates, sizes, colors and
slider values are all floats, it reaches almost everywhere. 155 functions
pass or return a float or double. In the wrapper, `set_spacing`,
`set_padding`, `slider`, `slider_value`, `rect`, `click` and `events()`
declare `NonFiniteFloat`, and so does every program that calls them.
Writing `set_spacing(panel, 12.0)` with a constant still makes the call
fallible: the charge is per signature, and a proven constant does not
discharge it.

**Since RAW-C-FLOAT-FFI-MILESTONE-1.md** a binding can write a C float or
double raw, `std::ffi::c::RawFloat` / `RawDouble`: the same C type, every
bit pattern carried, no admission at the boundary. The profile chooses,
per function and position (`representations`): Raven's slider and spin
box values, both ways, and the spin box's range (`Rslider_get_value`,
`Rslider_set_value`, `Rspin_box_get_value`, `Rspin_box_set_value`,
`Rspin_box_set_range`); the other 150 stay finite. A raw call is not
fallible, and the wrapper's finite accessors now state their admission
explicitly (`slider.slider_raw_value().float_to_float64()`), while the raw
accessors give the caller Raven's value as it is -- a spin box with an
unbounded range returns an infinity, which only the raw accessor can
carry. The setters keep Raven's own preconditions: a spin box ignores a
NaN (its source checks `value != value`), a slider has no such guard, so
`set_slider_raw_value` passes finite patterns only. The milestone also
removes floating admission as an obstacle to the callbacks of 7.1: a
callback parameter declared raw receives C's bits without a check that
could fail before its body runs.

### 7.5 Smaller frictions

* **Integer domains with identical ranges do not convert.** `ULong` and
  `std::abi::Usize` are both 0..2⁶⁴−1 here, but neither is admitted as the
  other:

  ```
  argument for parameter "length" cannot be proven to satisfy std::abi::Usize (argument type: std::ffi::c::ULong)
  ```

  `std::abi::usize(n)` converts, but declares two errors that cannot
  happen and that every caller must handle. An `int` reaches `ULong` only
  through a range guard (`if count < 0 or count > 4294967295: ...`).
* **`==` is type-blind** (by design: DECIMAL-ROUNDED-MILESTONE-1.md and
  others). `image.pixels.length() == 4 * w * h` compiled under
  `-warnings error` and was always false: `length()` is a `std::abi::Usize`,
  a struct with a `value` field. Only the desktop test's run caught it. A
  warning for `==` between operands whose static types can never be equal
  would have caught it at compile time.
* **Lists have no concatenation, map or fold, and loops yield no value.**
  Building `List[Event]` from the queue, or showing a list of events, takes
  a recursive helper over an index each time (as the 2048 workload recorded,
  POST-2048-PRODUCT-FIXES.md).
* **A constructor needs `nomethod`** (section 4). Its absence turns a title
  into a suggested receiver.
* **The generated enums are plain C constants.** `R_THEME_DARK` and
  `R_WIDGET_VBOX` are both `std::ffi::c::UInt`, so
  `Rwidget_create(R_THEME_DARK)` type-checks. This is the generator's rule
  (no nominal type per typedef or enum: C-BINDGEN.md, "Declaration
  mapping"), and the wrapper's Botlish enums (`Theme`, `Backend`,
  `EventKind`) are where the names become types.
* **Deployment of a shared library.** Botlish adds no rpath, so a program
  finds `libraven.so` through `LD_LIBRARY_PATH`. Linking Raven statically
  would need its own dependencies declared too (X11, libm, libdl). The
  package could do that with `extern c library ... static at`, but this
  was not attempted.

### 7.6 What worked as it is

The binding needed no new language or generator feature:

* Raven's handle-based design means most of the API needs no authority.
* The C float support, the layouts (27 of 27, all verified against C at
  run time), the profile's contracts and package-relative static archives
  all worked as documented.
* A context can own native pointers (CONTEXT-OWNED-AFFINE-STATE-MILESTONE-1.md).
* Real windows run under Xvfb on the Vulkan renderer.

## 9. Not done

* **macOS and Windows bindings.** The profile lists the Linux targets
  only. macOS needs the macOS SDK. Windows needs MSVC's headers, generated
  on Windows (ICY-TOWER-WINDOWS.md). Raven supports both platforms.
* **The callbacks of 7.1**, and so custom-painted widgets, virtual lists,
  synchronous raw-input handling, drop acceptance and worker tasks.
* **Most of the 921 functions have no wrapper.** The wrapper covers windows,
  panels, the common controls, actions, timers, themes, errors and
  synthetic input; the rest is reachable through the generated modules.
  Not wrapped: menus, lists and trees, the text editor, docking, dialogs,
  the color picker, timeline and node graph, styles, fonts and textures,
  translations, accessibility.
* **The bridge records the events the wrapper registers for** (the ones
  above, plus list views, spin boxes and menu items, which the wrapper does
  not create yet). Every further reporting callback is one more C
  function of the same three lines.
* **The pinned version.** Raven v0.1.3; `main` was 7 commits ahead when
  pinned, and the API "may still change before 1.0".

## 10. What to run when changing this

* **A change to the profile, or a new Raven release** (change the tag and
  commit): regenerate with the pinned toolchain
  (`tools/c-bindgen.tcl generate raven -target all` in an Ubuntu 26.04
  environment with `.devcontainer/setup-c-toolchain.sh`), commit the diff,
  and run `tools/c-bindgen.tcl check raven -target committed`. Then run
  `tests/c-bindgen.test` (its `cb-raven-*` need `tools/c-bindgen.tcl
  fetch raven` and `tests/cffi/raven.tcl`) and `tests/raven.test`.
* **A change to `packages/raven`, the bridge, `tools/raven-package.tcl`,
  `examples/raven` or `tests/raven/`:** run `tests/raven.test`. For its
  desktop test, build the desktop configuration
  (`BOTLISH_RAVEN_CMAKE_FLAGS="" tclsh9.0 tests/cffi/raven.tcl`) and
  install Xvfb and a Vulkan driver (`mesa-vulkan-drivers`). A change to the
  bridge's records or functions changes its ABI version: change it in
  `raven_bridge.c` and in `start` together.
* **A new or removed test:** update its census row
  (`audit/golden/migration/census/raven.tsv` or `c-bindgen.tsv`) and the
  names file, then regenerate the manifest
  (`audit/golden/migration/merge.tcl`).

The `c-bindgen` workflow runs all of it on Ubuntu 26.04, both test files
with no test skipped.
