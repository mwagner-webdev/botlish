# C-BINDGEN-LAYOUTS.md

> Partially superseded by C-FLOAT-FFI-MILESTONE-1.md: `float` and `double`
> fields are layout fields (`std::ffi::c::Float`, `std::ffi::c::Double`), verified by
> layouts-check.c and the runtime oracle like any scalar; the `float` and
> `double` blockers and pressure rows below are gone (SDL3 103 layouts now,
> Tcl 36 with Tcl_Obj, BoringSSL 119, Win32 1015), `long double` remains.

> Partially superseded by FIXED-LAYOUT-ARRAYS.md: a fixed array of
> representable elements is a layout field now, its extents probed per
> dimension. The blocked counts, pressure tables and sentinel statuses
> below are this milestone's; with arrays every binding gained exactly the
> records the "fixed arrays" counterfactual forecast (+3 Tcl, +11 SDL3, +19
> BoringSSL, +249 Win32), and the pressure report now weighs unions, Bool,
> floats, bitfields and flexible arrays (FIXED-LAYOUT-ARRAYS.md, section 12).

> Partially superseded by LAYOUT-UNIONS.md: a C union is a `union layout`
> and an anonymous member (an anonymous union, an anonymous struct inside a
> union) a synthetic layout of its own, so the `union` and
> `anonymous-overlay` blockers below are gone; an anonymous member's size
> and alignment are clang's record layout, verified after generation. With
> unions every binding gained the records the "unions" counterfactual
> forecast, counted as it counted them: Tcl 34, SDL3 85 and BoringSSL 117
> exactly, Win32 988 representable of which 985 emitted (3 anonymous members
> whose records a bitfield blocks are not emitted: nothing reaches them);
> anonymous structs inside unions, records of their own now, add to the
> totals (LAYOUT-UNIONS.md, "Forecast against actual").

C binding generation of native record layouts: the binding generator
(`tools/c-bindgen.tcl`, C-BINDGEN.md) now writes an ordinary Botlish
`layout` (BINARY-LAYOUT.md) for every complete C record whose every field the
layout language already represents, with the size, alignment and offsets
the target's C compiler gives it, and a manifest of every record it did not
lay out and why. The same milestone adds the `windows-x86_64-gnu` target and
a raw Win32 binding generated on Linux from MinGW-w64's headers.

> The C compiler decides the layout; Botlish records the result.

> The generator may interrogate a C implementation. The Botlish compiler
> must not become one.

Nothing in the compiler changed for this: a generated layout is source an
author could have written, compiled, viewed (`std::binary::native::view`), edited
(`std::binary::native::edit`) and written into byte storage (`std::binary::write`)
by the ordinary machinery of NATIVE-LAYOUT-VIEWS.md and
NATIVE-LAYOUT-WRITES.md. The layout language is unchanged.

## 2. Architecture

```
headers --clang -E--> preprocessed TU --cheader parser--> records (tags, typedefs, members)
                                                              |
                         records.tcl: Discover (candidates, names, anonymous members)
                                                              |
             probe (one C file of data directives, compiled to assembly, read back):
                 sizeof, _Alignof, __builtin_offsetof, member sizeof, array extents,
                 typedef and enum ABI, member conventions
                                                              |
                         Classify (each member: scalar | pointer | nested | blocker)
                                                              |
                 Order (dependency order, by value only) -> Settle (emitted or blocked,
                 transitive chains and root reasons) -> Name -> emission order
                                                              |
       emit.tcl: NS/layouts.bot      report.tcl: layouts.tsv, report rows, manifest lines
                                                              |
       verify.tcl: layouts-check.c (read back from layouts.bot), compiled for the target
```

New files: `tools/c-bindgen/records.tcl` (the record model), `pressure.tcl`
(the counterfactuals), `verify.tcl` (the static check), `oracle.tcl` (the
runtime oracle, test tooling only), the Win32 profile; the layout fuzzer and
the scaling fixture under `audit/c-bindgen/tools/`. The pipeline gained one
probe compilation (the layout facts) and one verification compilation per
target; everything else is the existing pipeline (C-BINDGEN.md section 2).

Candidates are the complete records the profile's public headers define and
every record those contain by value, from any header: a public record holding
a system header's record by value needs that record's layout too (none of the
five bindings has one; the report counts them). Incomplete public tags are
`opaque-only`. A record seen only through pointers from a system header is
`outside` (the API pressure counts it), never laid out.

## 3. Nominal identity vs layout

A C record is two facts in the binding, kept in two declarations:

* its **pointee identity**, the opaque struct of `NS::ctypes`
  (C-BINDGEN.md section 10): what a pointer to it points to, complete or not,
  one per C tag, the same on every target;
* its **layout**, `NS::layouts::NAME`: where a complete record's bytes are,
  on this target.

```botlish
# win32::ctypes
# struct _SYSTEMTIME (minwinbase.h), a complete C type: its layout is win32::layouts::SYSTEMTIME
opaque struct SYSTEMTIME:
    tag: unit
```

A signature keeps `std::ffi::c::Ptr[win32::ctypes::SYSTEMTIME]`; a program views
the memory with `std::binary::native::view(win32::layouts::SYSTEMTIME, p)`. The
layout is not the identity's definition and the identity is not a layout's:
Botlish has no way to say "this opaque type has that layout" and this
milestone adds none (NATIVE-LAYOUT-VIEWS.md: `NativeView[L]` is the address
word of any data pointer). The ctypes comment now names the layout (or
"whose layout is blocked (layouts.tsv)", or "seen through pointers only")
so a reader finds it.

A pointer field keeps its pointee's identity: `bgf_node *next` is
`std::ffi::c::Ptr[bgf::ctypes::bgf_node]`, never `Ptr[Void]`; a pointer to a
record whose layout is blocked, or to an incomplete one, is an ordinary
typed pointer and blocks nothing (`layout-pointer-blocks` is a mutant).
Function-pointer fields use the existing callback mapping
(`std::ffi::c::FnPtr[Fn{...}]`), its own blockers included (`unsupported-pointer`:
TclStubs holds variadic function pointers, `tcl_Panic` among them).

## 4. Representable subset

A record is `layout-direct` when it is complete and every member is one of:

* a C integer scalar: `char` .. `unsigned long long`, an integer typedef or
  an enum, the scalar the binding model's ABI probes confirm
  (`std::ffi::c::Int`, `std::ffi::c::ULong`, ...: target widths);
* a data or function pointer of the existing pointer mapping;
* a record with an emitted layout, nested by value (its fields designated
  `L.inner.x`).

Padding is the bytes no field covers; packing (`#pragma pack(1|2)`,
`__attribute__((packed))`) and alignment attributes
(`__attribute__((aligned(16)))`, on a record or a field) are whatever the
compiler made of the numbers. An anonymous struct member is promoted into its
record (its fields become the record's, as C sees them); an anonymous struct
of a named member gets a layout of its own (`bgf_member_anon_range`).

Everything else blocks the record, with a precise reason (`layouts.tsv`,
report "Layout blockers"):

| blocker | what | extra detail recorded |
|---|---|---|
| `fixed-array` | `T name[N]` | element category (char, wide-char, scalar, pointer, record, array, other), element C type, the bound as written, the extent the compiler computed |
| `flexible-array` | `T name[]` | the offset (no size) |
| `union` | a union record | |
| `anonymous-overlay` | an anonymous union member (its members overlap the record's) | |
| `bitfield` | `T name : W` | declared type, width |
| `float`, `double`, `long-double`, `complex` | floating members | |
| `c-bool` | C `_Bool` (`bool`) | never `std::ffi::c::Bool` in a layout; never a `U8` |
| `volatile`, `atomic` | qualified members | |
| `unsupported-field-type`, `unsupported-pointer`, `va-list`, `typedef-abi-mismatch`, `enum-unknown-abi`, `unresolved-typedef` | a type outside the ABI universe, or one the probes do not confirm | the model's own reason |
| `unsupported-calling-convention` | a function-pointer member with a convention the target does not take as its default | |
| `empty-record`, `probe-rejected`, `layout-cycle` | defensive | |
| `nested-layout-blocked` | a record held by value is blocked | the member, the dependency, and the chain down to the first direct blocker: `field inner (struct bgf_outer_blocked, field) -> struct bgf_chars -> fixed-array` |

The fixture's `bgf_flagged_rect` (a rect beside `bgf_flag`, a record
holding a `_Bool`: blocked transitively), `bgf_points4` (`bgf_point
pts[4]`: an array of a representable record, still an array) and
`bgf_matrix` (`int m[2][3]`) are blocked, not flattened: no
array becomes N synthetic fields (`layout-array-flattened` is a mutant).
Win32's `BOOL` is `int` and binds as `std::ffi::c::Int`: only the C `_Bool` type
is `c-bool`.

## 5. Probe method

No layout rule is implemented anywhere. One C file per target asks the
compiler, through the existing data-directive probe (C-BINDGEN.md section 5:
`.quad`/`.long` directives of constant expressions, compiled to assembly with
`-S` and read back):

```c
/* rec:struct bgf_frame */  sizeof(bgf_frame), _Alignof(bgf_frame)
/* fld:struct bgf_frame:1 */ __builtin_offsetof(bgf_frame, bounds), sizeof(((bgf_frame *)0)->bounds)
/* dim:...:I */              sizeof(((T *)0)->m) / sizeof(((T *)0)->m[0])   (array extents)
/* ccfld:...:I */            __builtin_types_compatible_p(...)                (member conventions)
```

* A record is named by a spelling C accepts: its first typedef, else
  `struct TAG`, else (anonymous) `__typeof__` of its container's member.
* A macro whose name is a probed identifier is `#undef`'d after the headers
  (the fixture's `#define late_value code` would otherwise make
  `offsetof(bgf_late, late_value)` the offset of `code`:
  `layout-probe-undef-dropped` is a mutant).
* A member's representation is the binding model's existing type mapping:
  its integer typedef and enum ABI probes (`td:`, `enum:`) decide its scalar;
  the layout probe decides only numbers.
* A promoted member's offset is absolute in its record
  (`__builtin_offsetof` through the promoted path); a nested layout's fields
  are its own layout's, at the nested member's offset.

The probe is one more compilation per target (fixture 64 ms of layout work,
Win32 2.0 s; section 19). The probes run for every target of a profile; the
fixture's four targets show the target model at work: `bgf_longs`
(`char c; long l; unsigned long ul; long long ll; void *p; int i; unsigned
long long ull`) is 56 bytes with `l` at 8 on LP64 and 48 bytes with `l` at 4
on windows-x86_64-gnu (LLP64).

Packing, from the fixture on linux-x86_64 (all agree with GCC):

| record | how | sizeof | _Alignof |
|---|---|---:|---:|
| `bgf_packed1` | `#pragma pack(1)`: u8, u32, u16 | 7 | 1 |
| `bgf_packed2` | `#pragma pack(2)` | 14 | 2 |
| `bgf_packed_attr` | `__attribute__((packed))` | 11 | 1 |
| `bgf_aligned` | `__attribute__((aligned(16)))` on the record | 16 | 16 |
| `bgf_aligned_field` | holding `bgf_aligned` by value | 32 | 16 |
| `bgf_nested_packed` | default record holding `bgf_packed1` | 12 | 4 |
| `bgf_packed_outer` | `#pragma pack(1)` record holding an unpacked one | 11 | 1 |

## 6. Generated naming

A layout's Botlish name is deterministic and collision-safe, a function of
the records alone (never of discovery or probe order):

* the first typedef naming the tag directly (`typedef struct bgf_coll_a
  bgf_coll` gives `bgf_coll`), else the tag, else, for an anonymous record of
  a named member, the container's name and the member's
  (`Tcl_ObjInternalRep_twoPtrValue`, `bgf_member_anon_range`);
* several typedefs of one record give one layout (`bgf_multi`, aliased by
  `bgf_multi_alias` and `bgf_multi2`: listed in its comment and manifest row);
* a name Botlish reserves gets a trailing `_`: a keyword (`typedef struct
  bgf_kw {...} loop` is `loop_`, its members `fn_`, `type_`) or a built-in
  type (`struct List` is `List_`);
* two records one name would give it in a fixed preference (named by a
  typedef of that name, then a tag of that name, then synthesized; then by
  key), the others `_struct`/`_union`, then `_2`, `_3`: the fixture's
  `struct bgf_coll_a` (typedef `bgf_coll`) is `bgf_coll` and `struct
  bgf_coll` is `bgf_coll_struct`.

Field names are the C member names (a reserved one with `_`); promoted
members keep their own names. The emission order is translation-unit order
with every nested layout before its first user.

## 7. The layout manifest

`layouts.tsv` (beside `manifest.txt` and `report.tsv`) has a row per record
and a row per member, for later pressure analysis:

```
kind   record           index name  status        offset size align c                type          detail
record struct bgf_chars -     -     layout-blocked -      20   4     struct bgf_chars -             typedefs=bgf_chars; identity=bgf::ctypes::bgf_chars; header=include/bgf/bgf_records.h:181; blockers=fixed-array: ...; roots=fixed-array; pointed-by=1
field  struct bgf_chars 0     len   scalar         0      4    -     int len          std::ffi::c::Int   c=len
field  struct bgf_chars 1     name  fixed-array    4      16   -     char name[16]    -             c=name; element=char char; bounds=16; extent=16; blockers=...
```

Every record (struct or union, complete or not, public or a by-value
dependency), its typedefs, opaque identity, header location, status, layout
name, sizeof, _Alignof, every member's name, C declaration, Botlish type,
offset, size and category, every blocker, the by-value dependencies, the
root reasons, and how many bound APIs point to it. Its first line names the
target and the toolchain (`toolchain clang x86_64-w64-mingw32 (Ubuntu clang
version 18.1.3 ...)`); `manifest.txt` repeats it as `layout_abi` with the
counts (`layout_count`, `layout_blocked`). `report.txt` gained the sections
"Records and layouts", "Layout blockers", "Layout pressure" and "API
pressure"; `report -why NAME` explains a record by its key or by a typedef
naming it:

```
$ tclsh9.0 tools/c-bindgen.tcl report win32 -target windows-x86_64-gnu -why OVERLAPPED
typedef OVERLAPPED: generated (opaque in win32::ctypes): identity OVERLAPPED; struct _OVERLAPPED
record struct _OVERLAPPED: not generated (layout-blocked): anonymous-overlay,nested-layout-blocked
```

## 11. Win32 GNU x86-64

The `win32` profile (`tools/c-bindgen/profiles/win32.tcl`) binds the raw
Win32 API of MinGW-w64 11.0.1's `<windows.h>` for **windows-x86_64-gnu**:
Windows x86-64 with the GNU ABI, as MinGW-w64's headers and clang's
`x86_64-w64-mingw32` target give it. It is generated entirely on Linux, from
the cross toolchain's own headers (Debian and Ubuntu's
`mingw-w64-x86-64-dev`), and is MinGW evidence: it claims nothing about MSVC.

**The target.** `core/cabi.tcl` gained the row `windows-x86_64-gnu {os
windows arch x86_64 model LLP64 charSigned 1 triple x86_64-pc-windows-gnu}`.
It equals windows-x86_64's (MSVC's, `x86_64-pc-windows-msvc`) in every
column the table has, and is a different target: C facts probed with one
toolchain are that toolchain's (the toolchains differ in `long double`,
bitfield allocation, the C runtime and import libraries), a HIR built for
one is refused for the other (interchange, the cache, NATIVE TARGET), and
the C convention is Cranelift's Windows fastcall for both. The toolchain
adapter maps it to clang `--target=x86_64-w64-mingw32`; windows-x86_64 has no
toolchain configuration (no MSVC tool exists to generate for it), and
`layout-windows-gnu-as-msvc` is a mutant. (Since ICY-TOWER-WINDOWS.md,
windows-x86_64 is clang's `x86_64-pc-windows-msvc`, generated only on
Windows, where clang finds MSVC's and the Windows SDK's headers: the Icy
Tower build generates its SDL3 binding there; none is committed.)

**Explicit configuration.** The translation unit is `<windows.h>` with
exactly the profile's defines -- nothing comes from the shell (the
`BOTLISH_C_*` extra-word knobs are cleared for it):

```
WIN32_LEAN_AND_MEAN UNICODE _UNICODE _WIN32_WINNT=0x0A00 WINVER=0x0A00
NTDDI_VERSION=0x0A000000 STRICT NOMINMAX
```

The headers are pinned by MinGW-w64's own version macros, as a fetched
source is pinned by its commit (`version {__MINGW64_VERSION_MAJOR 11
__MINGW64_VERSION_MINOR 0 __MINGW64_VERSION_BUGFIX 1}`; headers of another
version are refused, `cb-win32-version-pinned`), and the manifest records
that revision, the preprocessing command (no include directory but the
toolchain's own) and clang's version. MinGW-w64's
C runtime and annotation headers (`_mingw*.h`, `corecrt*.h`, `sal.h`, ...)
are private: their declarations are not the Win32 API.

**A and W.** With UNICODE, every generic name is the W API's: `FooA` and
`FooW` are both bound as declared, and the generic macro `Foo` (`#define
CreateFile CreateFileW`) is an alias of `FooW`'s symbol (597 aliases).
STRICT gives every handle type its own identity (`HWND` is `struct HWND__
*`, 4 bytes, a layout of its own).

**Import libraries.** A Win32 header declares functions of several DLLs. A
profile library rule of a new kind, `{targets * symbols {kernel32 user32
gdi32 advapi32 ...}}`, attributes each bound function to the first library
whose MinGW-w64 import library (`clang -print-file-name=libNAME.a`, read by
`llvm-nm`) defines its link symbol: the toolchain's answer, never a table of
names. A symbol several define takes the first; the manifest lists every one
(`import_multiple VerLanguageNameW kernel32 version`); a function none
defines is unsupported (`no-import-library`: 75 functions and 28 macros --
compiler intrinsics, WinMain/wWinMain, `__C_ASSERT__`, API-set-only
functions such as VirtualAllocFromApp, and APIs MinGW-w64 11's import
libraries do not define). Each module declares the libraries of its own
functions (`win32::fileapi` links kernel32).

**Calling conventions.** `WINAPI` is `__attribute__((__stdcall__))`, which
the x86-64 targets ignore. A function declaring a convention is bound when
the compiler says its type is the plain one
(`__builtin_types_compatible_p` against the type with the convention
dropped; `convention_default stdcall 3176` in the manifest, and
`ms_abi 1` for the fixture on windows-x86_64-gnu), and blocked
(`unsupported-calling-convention`) where it is not (`ms_abi` on Linux
x86-64). No stdcall or fastcall surface exists in Botlish and none is added:
the probe only proves that the declared convention is the target's default.

## 12. MinGW scope

What this milestone does and does not do for Windows:

* **GNU only.** The target, the profile, the headers, the import libraries,
  the probes and the second compiler are MinGW-w64's. No MSVC header,
  `cl.exe`, `clang-cl`, Windows SDK or GNU-vs-MSVC comparison is used or
  claimed; the binding's description, banner, manifest and report say
  "GNU ABI (MinGW-w64), not MSVC". MSVC is a separate milestone.
* **Generated, not run.** No Windows binary is executed (no Wine, no Windows
  runner). The evidence is the compiler's (clang and GCC) and the import
  libraries'; the runtime oracle runs only on the Linux host's layouts.
* **No Windows backend.** No PE output, Windows runtime, syscall layer or
  Windows native execution; the native driver refuses the target
  (NATIVE TARGET). x86-64 only: no 32-bit Win32, no stdcall or fastcall
  surface.
* **No Windows SDK vendored, nothing downloaded** but the distribution's
  MinGW-w64 packages, which CI installs.
* **No Ptr-from-Int** for INVALID_HANDLE_VALUE and its kind, and no wrapper
  protocol inferred (handles stay `Ptr[Void]` or their STRICT identity).

## 15. Verification

Every emitted layout is checked by the C compiler at generation, by a second
compiler, and at run time:

**`layouts-check.c`** (`verify.tcl`), generated and compiled for the target
with the profile's defines and includes, one line per field:

```c
BOTLISH_RECORD(struct _SYSTEMTIME, 16, 2, "SYSTEMTIME");
BOTLISH_SCALAR(struct _SYSTEMTIME, wYear, 0, 2, 0, "SYSTEMTIME.wYear");
...
BOTLISH_POINTER(struct _PROCESS_INFORMATION, hProcess, 0, 8, "PROCESS_INFORMATION.hProcess");
BOTLISH_NESTED(struct bgf_rect, origin, 0, 8, "bgf_rect.origin");
```

`_Static_assert`s of sizeof, _Alignof, every offset, and per field its class
(`__builtin_classify_type`: integer, pointer, record), width and signedness
(from core/cabi.tcl's table of the target), no `_Bool` (`(T)2 == 2`: GCC
classifies `_Bool` as an integer), and a nested record's size. Its numbers
are **read back from the generated `layouts.bot` text**, not from the
generator's model, so a corrupted emission or manifest fails the compile,
naming the layout and the field; the C names come from `layouts.tsv`. A
disagreement stops generation. It is committed beside the binding.
`cb-layout-verified` corrupts a size, an alignment, an offset by one and a
field's width and class and expects each to fail.

**A second compiler.** GCC compiles the same file: the host's `cc` for the
host target, `x86_64-w64-mingw32-gcc` for windows-x86_64-gnu (all 564 Win32
layouts and the fixture's), `aarch64-linux-gnu-gcc` for linux-aarch64
(`cb-layout-second-compiler`, `cb-win32-verified-gcc`), and the host's `cc`
for every layout of the Tcl, Tcl stubs, SDL3 and BoringSSL bindings
(`cb-layout-gcc-bindings`); `aarch64-linux-gnu-gcc` agrees on their
linux-aarch64 layouts too (29, 70 and 52; checked by hand).

**The runtime oracle** (`tools/c-bindgen/oracle.tcl`, test tooling: nothing
the generator or the compiler loads) builds, for every emitted layout of a
binding on the host, a C library and a Botlish program (a direct module) and
runs it on both native backends:

1. C fills every field of a record with typed stores of distinct values
   (`memcpy` from a typed temporary, so `const` members are written too);
   Botlish reads every field through `std::binary::native::view` and compares;
2. Botlish stores distinct values into every field of C memory filled with
   `0xA5` through `std::binary::native::edit`/`std::binary::store` (pointer fields
   with pointers C handed out); C checks every field and that every padding
   byte is still `0xA5`;
3. Botlish builds the record in `std::abi::bytes::MutableBytes` with
   `std::binary::write` and `std::binary::write_foreign`; C checks that image, its
   padding zero; `std::binary::parse` reads a pointer-free one back;
4. `std::binary::layout_length` and `std::binary::layout_alignment` are C's sizeof and
   _Alignof.

Fixture 286 checks, Tcl 329, SDL3 826, BoringSSL 406: no failure on
cranelift or cranelift-generic (`cb-layout-oracle-fixture`,
`cb-tcl-layouts`, `cb-sdl3-layouts`, `cb-boringssl-layouts`). A corrupted
offset (`bgf_scalars.us` at 10 instead of 8) fails 3 checks.

**Acceptance** (`cb-layout-ordinary`): a program over a generated layout
(bytes in, a LayoutStruct out, bytes back) runs on all four backends,
through HIR interchange in a fresh process and through the front-end cache,
with no C compiler at compile time. Win32's layouts compile for their
target (section 11).

## 16. Fuzzing

`audit/c-bindgen/tools/layout-fuzz.tcl` generates freestanding headers of
random records -- every C integer type, stdint names, typedef chains, enums
of either sign, data and function pointers (to earlier records, to itself, to
incomplete ones, two levels), earlier records nested by value, anonymous
members, `#pragma pack(N)`, `packed` and `aligned` around and inside them --
and, in some records, a field the layout language lacks (arrays of int,
char or a record, a flexible array, a union, a bitfield, a float, a double, a
`_Bool`, or a record holding one by value). For each it generates the
binding for a target and checks it against its **own model** (which records
are layouts, their blockers and roots, every field's name and Botlish type
from its own table of the target's data model), against **GCC** (every
size, alignment and offset through its own C designators: run on the host,
static assertions for a cross target) and, on the host, against the
**runtime oracle** on both native backends.

Runs, each of four programs of ten records: seeds 1, 2, 3, 21, 31 and 41 on
the host (linux-x86_64); seeds 1 to 3, 21 and 31 for windows-x86_64-gnu and
linux-aarch64; seeds 7, 21 and 31 for macos-aarch64 (no second compiler
there: the model and the generator's own static check); seed 9 under
`-gc-stress 1`; seed 5 with 24 records a program. 0 disagreements. One
first run (seed 21) reported a disagreement that was the fuzzer's own: it
had drawn a struct whose only member is a flexible array, which C rejects;
the fuzzer now draws one only after a named member. CI runs four programs of
24 records per target per run.

## 18. Determinism

Generation is deterministic: no time, temporary path, host path, hash or
directory order reaches the output; `check` regenerates every committed
target and compares byte for byte (all six profiles current after every
change of this milestone), and `cb-fixture-deterministic` generates twice and
compares. Layout names depend only on the records (section 6), the emission
order on the dependency graph and translation-unit order
(`layout-order-unstable` is a mutant), the verification file only on the
emitted text.

## 21. Recommended next representation milestone

Measured, not chosen in advance (sections 13 and 14):

1. **Fixed arrays of fixed extent** are the largest single missing
   representation: 282 records and 353 bound APIs across Tcl, SDL3,
   BoringSSL and Win32, first in three of the four. The demand is mostly
   one-dimensional arrays of integers and characters (167 char, 64
   wide-char, 76 other integer fields; 57 of records, 4 of pointers, 3 of
   floats, 2 multi-dimensional), whose extents the compiler
   already computes (`extent=` in the manifest, macro expressions

   Tcl_DString's buffer.
2. **Unions**, designed with arrays rather than after them: alone they
   recover 126 records and 122 APIs, but with arrays they turn 408 records
   into 509 and 475 APIs into 680 (BoringSSL's contexts, Win32's OVERLAPPED
   and LARGE_INTEGER -- overlapped I/O, I/O completion, file positions).
   A union is an overlap, which the layout language rejects today
   (BINARY-LAYOUT.md); representing it is a decision about reading and
   writing overlapping fields, not a generator change.
3. Then by binding: **floats** for SDL3 (16 records, 25 APIs), **doubles**
   only with unions (Tcl_Obj: 204 Tcl APIs), **Bool fields** for SDL3's GPU
   and event records (14), **bitfields** for Win32 and CBB (15 records, 10
   APIs). Flexible arrays and long double have no measured pressure.

Independently of layouts, the measured API pressure says most Tcl, SDL3 and
BoringSSL record pointers go to incomplete records, which no representation
changes; Win32 is the binding where layouts already reach 87% of the APIs
that point to records.

## 22. What to run when changing this

If you change `tools/c-bindgen/` (records, pressure, verify, oracle, emit,
report, generate, model, profile), `tools/cheader/`, a profile or the
fixture: `tclsh9.0 tests/c-bindgen.test`, `tools/c-bindgen.tcl check
PROFILE -target committed` for fixture, tcl, tclstubs, boringssl, sdl3 and
win32 (regenerate and review the diff when it is intended),
`audit/c-bindgen/tools/fuzz.tcl` and `audit/c-bindgen/tools/layout-fuzz.tcl`
(several seeds, host and `-target` each cross target),
`audit/c-bindgen/tools/layout-scale.tcl` for the layout pass, and
`audit/c-bindgen/tools/mutate.tcl` (every mutant must apply and be killed).
A change to the target table runs the target model's harnesses (AGENTS.md,
"Compilation targets"). The Win32 tests need MinGW-w64 11.0.1's
`mingw-w64-x86-64-dev`, `llvm-nm` and `gcc-mingw-w64-x86-64`.
