# Capture-explicit StringRegion companions: `char_at` becomes virtual

Milestone date: 22 September 2026. Prior source revision: `b922d36`
("Regenerate the scalar assembly audit corpus"), the nested-closure-
allocations milestone's own final commit. That milestone's own
`hir/blockescape.tcl` declined to virtualize a candidate the moment
`hir::stringregion::wants` held for it, and named `char_at` -- the sole
remaining recurrent Block allocation site in `bench/refined-checks.ir`
(1,200 of 1,201 Block objects, the 800+400 sites this milestone closes) -- as
exactly that excluded case. This milestone removes the exclusion by giving
a capture-explicit internal variant its own StringRegion result companion,
so `char_at` itself becomes blockescape-virtual while its region-requesting
callers keep working. Evidence generated by this milestone is under
`audit/capture-explicit-stringregion/`.

## Files changed

- `hir/blockescape.tcl` -- the `hir::stringregion::wants` exclusion in
  `Bindings`'s eligibility fixpoint is removed (three lines replace a
  sixteen-line conservative decline); the module no longer takes
  `stringregion` as an argument at all (`analyze`/`Bindings` drop the third
  parameter -- nothing inside the module consulted it for any other
  purpose). Header and entry-point comments updated to describe the new,
  decoupled relationship with `hir::stringregion.tcl` (native/lower.tcl's
  Call now composes the two analyses, rather than one excluding candidates
  on the other's behalf).
- `native/lower.tcl` --
  - `program`'s analysis wiring: `hir::blockescape::analyze` is called with
    two arguments now; the comment explaining "stringregion before
    blockescape, so blockescape can decline" is replaced with a comment
    explaining the two analyses are now independent (ordering is no
    longer a soundness dependency, only kept for determinism).
  - New `InternalRegionCompanionRef`/`InternalRegionCompanionFunction`
    (mode `internalregion`): the composition itself -- `InternalFunction`'s
    own env=0/capture-explicit-trailing-parameters shape, generated from
    the *same instance and body* as `RegionCompanionFunction`, ending in
    the same `retmulti` of region fields instead of `ret`ing a
    materialized String. Wired into `program`'s dispatch switch and
    function-ordering table exactly like every other variant kind.
  - New `FlattenedVirtualRegionCall`: `FlattenedVirtualCall`'s own region-
    result sibling -- resolves the callee's flattened captures the same
    way, in the same order, and dispatches to `InternalRegionCompanionRef`
    via a direct `callmulti` (never `callenvmulti`: there is no
    environment register).
  - `Call`'s early Block-virtualization dispatch: the `!$wantRegion` guard
    that used to skip virtualized-binding handling entirely for a
    region-result call is removed; the dispatch now branches on
    `$wantRegion` to choose `FlattenedVirtualCall` or
    `FlattenedVirtualRegionCall`, both fed by the *same* flattened capture
    list (`hir::blockescape::captures`), computed once.
  - Header comments: a new "Composing with String regions" subsection
    under "Block virtualization" documents the composition, the mismatch
    it resolves, and the demand-driven/no-fake-environment discipline; the
    "String regions" section gets a short cross-reference explaining that
    a `remote` region whose callee is blockescape-virtual is intercepted
    before ever reaching `RegionCompanionFunction`/`callenvmulti`.
- `tests/native-block-escape.test` -- 20 new tests: a minimal independent
  fixture (`at`/`scan`, unrelated to `Emailish?`/`web.tcl`), a mixed
  ordinary+region-consumer fixture, an escaping-closure-coexisting-with-a-
  virtualized-region-closure fixture, a GC-stress fixture mixing region and
  ordinary calls to the same virtualized closure inside a self-tail loop,
  bounds-error and Unicode/astral parity fixtures, the four
  `-block-escape-opt`/`-string-region-opt` flag combinations, and five
  `refined-checks.ir`-specific tests locking in the acceptance numbers
  (allocation counts, NIR shape, flattened captures, GC stress, unchanged
  self-tail loop count).
- `audit/capture-explicit-stringregion/` -- generated evidence (NIR/CLIF,
  allocation and root reports, corpus and benchmark comparisons) for the
  before/after states.

No change to `core/`, `surface/`, `lib/web.tcl`, `lib/web.bot`, any
`examples/stdlib/*.bot` source, `hir/stringregion.tcl`, or `native/src/`
(Rust): this is purely a compiler-side representation composition, using
exactly the NIR ops, ABI shapes (env=0 functions, `results=N`/`retmulti`/
`callmulti`), and runtime the block-escape and StringRegion milestones
already had. `hir/stringregion.tcl` needed no change at all -- it already
classified a `remote` region purely by specialize-instance identity, never
by how the callee happens to be represented at lowering time.

## Current function-variant architecture (re-established from HEAD)

Before this milestone, `native/lower.tcl`'s `program` built at most six
kinds of NIR function per used specialize instance, each demand-driven
(only entered when some other function's lowering actually asks for it,
via the `pending` work-list and a `*Ref` helper):

| mode | builder | ABI | when |
|---|---|---|---|
| `canonical` | `Function` | `env=1` (or `env=0` if envless), ordinary `ret` | always reachable, unconditionally built for `program` + every instance a `FunctionRef`/`GenericRef` names |
| `companion` | `CompanionFunction` | same instance/body, `retmulti` of `hir::escape` fields | `hir::escape::wants` (List scalar-replacement companion) |
| `region` | `RegionCompanionFunction` | same instance/body, `retmulti` of `(base,start,end)` | `hir::stringregion::wants` (StringRegion companion) |
| `internal` | `InternalFunction` | `env=0`, flattened captures as ordinary trailing params, ordinary `ret` | `hir::blockescape::wants` (de-closure conversion) |
| `fields` | `FieldsFunction` | same instance/body, virtualized List *parameters* as trailing field registers | `hir::escape::paramWants` |
| `fieldscompanion` | `FieldsCompanionFunction` | `fields` + `retmulti` | both of the above |

Two independent dimensions were already visible in this table before this
milestone, exactly as the milestone brief's #4 anticipated:

- **capture representation**: canonical (a real closure/environment
  register, `env=1`, `capture I` loads) vs. capture-explicit (`env=0`,
  captures as ordinary trailing parameters -- `internal`/`fields`/
  `fieldscompanion`).
- **result representation**: ordinary (`ret` of one value) vs. StringRegion
  (`retmulti` of three fields, `region`/`fieldscompanion`-adjacent) vs.
  List-scalar (`retmulti` of N fields, `companion`).

But the *cross product* of "capture-explicit" and "StringRegion result" had
no entry: `internal` only ever produced an ordinary result, and `region`
only ever took a canonical (`env=1`) closure. `char_at` needed exactly that
missing cell.

## Why `char_at` could not virtualize before this milestone

`hir/blockescape.tcl`'s eligibility fixpoint (`Bindings`, HEAD before this
milestone) removed a candidate `b` from the eligible set whenever:

```tcl
set linst [dict get $singleInstance $b]
if {$linst eq "" || [hir::stringregion::wants $stringregion $linst]} {
    dict set eligible $b 0
    ...
}
```

`char_at`'s own callee instance is exactly a `hir::stringregion::wants`
target: `char_at(labelEnd) == "."` and `char_at(localEnd) == "@"` are
immediate `==` operands (Class A, already StringRegion-eligible before the
String-view milestone), and `is_local_char(char_at(i))`/
`is_label_char(char_at(i))`/`is_tcl_alpha(char_at(i))` are
`ConsumingParams`-eligible classification arguments (Class B/C, made
region-eligible by the String-view milestone). So every one of `char_at`'s
five call sites (`scan_local`, `scan_label`, `scan_alpha`, `domain_loop`
twice) asked for a region result, `hir::stringregion::wants` was `true` for
both of `char_at`'s specialize instances, and the guard above declined
virtualization unconditionally -- not because any call site was unsafe to
virtualize, but because the only region companion that existed
(`RegionCompanionFunction`) took a real closure: `native/lower.tcl`'s
`Call` reached it exclusively through `callenvmulti`, which reads
`capture 0` out of an actual `ClosureObj`. A capture-explicit candidate, by
definition, never builds one. That is the "architectural mismatch" the
milestone brief names: **a StringRegion result companion existed in only
one calling-convention shape (environment-bearing), and `char_at`'s only
representation option (capture-explicit) could not supply that shape.**

## The new representation: `InternalRegionCompanionFunction`

The fix composes the two existing shapes rather than inventing a third:

```tcl
proc native::lower::InternalRegionCompanionFunction {id} {
    ...
    # exactly InternalFunction's own parameter/capture setup:
    set rawParams [RawParams $id $instance $params]
    foreach b $params raw $rawParams { ... }               ; # ordinary params
    set captureBindings [dict get $captureLists $region]
    foreach b $captureBindings { dict set fn locals $b [list reg [NewReg fn]] }
    ...
    # exactly RegionCompanionFunction's own body-ending:
    set fields [Expr fn [lindex $body end] region]
    if {$fields ne "never"} { Emit fn "retmulti [join $fields { }]" }
    ...
}
```

It is not a special case for `char_at`: it is generated for *any* used
specialize instance that is simultaneously named by
`hir::blockescape::wantedInstances` (some binding's flattened-capture
target) and `hir::stringregion::wants` (some caller demands its region
form) -- the same generic, name-independent proof both existing analyses
already give per instance, never by source name, file, or a
`web.tcl`/`Emailish?` check anywhere in the new code (the milestone's #33).
`InternalRegionCompanionFunction`'s body lowering (`Expr fn ... region`,
the exact same call `RegionCompanionFunction` makes) reuses the entire
existing StringRegion body-lowering machinery -- `TryStringRegionOp`,
`RegionCheck`, `EmitRegionConsumerBody`'s downstream consumers -- with zero
duplication (the milestone's #32).

## Variant identity, reuse, and demand-driven generation

Every variant in this table -- including the new one -- is keyed by
`(InstanceId, mode)` (`native::lower::Key`) and built at most once, the
first time some other function's lowering asks for it via a `*Ref` helper
appended to the shared `pending` work list (`program`'s
`while {$pending ne ""} { ... }` loop, unchanged by this milestone). A
region companion is therefore identified by the same semantic identity as
every other variant here -- specialize InstanceId, itself resolved from a
Block's ExprId/BindingId by `hir::specialize.tcl` -- never by source name
or call site, and `InternalRegionCompanionRef` returns the exact same
placeholder for a repeated request, so two call sites (or a call site and a
self-tail backedge) demanding the same instance's region companion always
get one shared compiled function (verified directly: `refined-checks.ir`'s
`char_at` has 12 `callmulti` call sites across its two specialize instances,
but only 2 `char_at` functions total in the emitted NIR -- see below).
Nothing is built speculatively: `char_at`'s *ordinary* internal variant
(`InternalRef`) is never referenced anywhere in `refined-checks.ir` (every
one of its five call sites is region-eligible), so it simply never enters
`pending` and never exists in the compiled program -- confirmed by the
"NIR before/after" section below.

## Capture ordering and representation

`InternalRegionCompanionFunction` reads its own trailing capture
parameters from `native::lower::captureLists`, populated for every
`wantedInstance` by `program`'s existing override step:

```tcl
foreach pair [hir::blockescape::wantedInstances $hirProgram $spec $blockescape] {
    lassign $pair wantedId label
    set wantedBlock [dict get [hir::specialize::instance $spec $wantedId] block]
    dict set captureLists $wantedBlock [hir::blockescape::captures $blockescape $wantedId]
}
```

This is the exact same dict entry `InternalFunction` reads for the ordinary
internal variant of the same instance -- not a second, independently
derived list. `FlattenedVirtualCall` (ordinary-result dispatch) and
`FlattenedVirtualRegionCall` (region-result dispatch) are likewise fed the
same `hir::blockescape::captures $blockescape $flattenedTarget` value from
`Call`'s own single call site, computed once and passed to whichever of
the two is chosen. So a candidate's ordinary internal variant and its
internal region companion agree on capture identity, order, and
representation (raw Int, Bool, managed String, ...) *by construction*, not
by a second proof: there is only one flattened capture list per instance,
consulted by every variant that needs it.

## Ordinary vs. region-result call dispatch

`Call`'s early Block-virtualization dispatch (`native/lower.tcl`) now
reads:

```tcl
if {$wantVirtual eq "" && $targetKind eq "block"
        && [hir::kind $hir $calleeExpr] eq "ref"} {
    set flattenedTarget [... hir::blockescape::virtual ...]
    if {$flattenedTarget ne ""} {
        set captureBindings [hir::blockescape::captures $blockescape $flattenedTarget]
        if {$wantRegion} {
            if {![hir::stringregion::wants $stringregion $flattenedTarget]} {
                throw {NATIVE BUG} ...
            }
            return [FlattenedVirtualRegionCall fn $e $node $target $flattenedTarget $captureBindings]
        }
        return [FlattenedVirtualCall fn $e $node $target $flattenedTarget $captureBindings]
    }
}
```

`calleeExpr` (the `ref` to the virtualized binding) is never evaluated in
either branch -- there is no Block value to produce, no closure register to
load, whichever result form the call site wants. This resolves at the call
site, from HIR-level facts already known before any code is emitted
(`hir::blockescape::virtual` and `hir::stringregion::wants`, both
per-instance queries), so a mixed program -- one caller wanting an ordinary
String, another wanting a region, from the very same virtualized binding --
naturally gets both `InternalRef` and `InternalRegionCompanionRef` entered
into `pending`, and both variants coexist for the one instance
(`blockescape-region-companion-mixed-*` tests).

## Analysis interaction: `hir::blockescape.tcl` / `hir::stringregion.tcl`

The dependency the nested-closure milestone introduced ("stringregion
before blockescape, so blockescape can decline a region-wanted candidate")
is removed, not merely reordered: `hir::blockescape::Bindings` no longer
takes a `stringregion` argument at all, and nothing inside
`hir/blockescape.tcl` consults StringRegion facts any more. The two
analyses are now genuinely independent, composed only at lowering time in
`native/lower.tcl`'s `Call`. `program` still computes `stringregion` before
`blockescape` (kept for determinism/readability, not correctness) --
reassessed per the milestone's #74, the outcome is the second one it
names: the dependency could be weakened away entirely, not merely
"still useful."

This is also the central design shift the milestone's #75 asks for: the
old code was an *exclusion* ("if stringregion wants B, B cannot
virtualize"); the new code is a *positive capability* ("if B virtualizes
and stringregion wants B, ensure its region companion exists") --
literally, "ensure it exists" is exactly what `InternalRegionCompanionRef`
being demand-driven and idempotent already provides, so no separate
"ensure" step was needed beyond calling it from the one call site that
needs it.

## Self-tail interaction

`char_at` itself is never self-tail recursive (`substring(v, i, i+1)` has
no recursive call at all), so `FlattenedVirtualRegionCall`'s own self-tail
branch is dead code for this corpus -- included defensively, mirroring
`FlattenedVirtualCall`'s identical branch, in case a future region-eligible
candidate ever is self-tail recursive. What does matter here is
`scan_local`/`scan_label`/`scan_alpha`/`domain_loop`'s *own* self-tail
loops, which call `char_at` (now virtual, in region form) once per
iteration from inside the loop body, then loop back via `tail`. This
composition needed no change to the self-tail/`tail` backedge machinery at
all: `char_at`'s region companion call is an ordinary statement inside the
loop body, ahead of the `tail` instruction, exactly as it always was --
confirmed below by an unchanged `tail`-instruction count (11, identical
before and after this milestone) in `refined-checks.ir`'s NIR.

## Effect-summary interaction (`may_error`/`may_gc`)

`InternalRegionCompanionFunction` emits ordinary NIR (`op regioncheck`,
`op iadd`, `retmulti`) that Rust's `summarize_call_effects`
(`native/src/nir.rs`) already classifies generically, by op table lookup
(`op_may_error`/`op_may_allocate`) and a whole-program call-graph fixpoint
-- no Rust code was touched, and none needed to be: the new function
participates in that fixpoint exactly like every other NIR function,
automatically (the milestone's #23, #25).

Concretely, for `char_at`'s own body: `RegionCheck` is `may_error=true` (it
is the same RANGE-fallible bounds check the materializing `substring` path
already runs) and *not* in `op_may_allocate`'s table -- so region-checking
itself contributes no allocation bit, exactly as expected. But `char_at`'s
own `i+1` is lowered through `IAdd`, which *is* in `op_may_allocate` (raw
integer addition can promote to a heap `BigInt` on overflow) -- and that
bit was **already** set before this milestone, on the old canonical,
closure-taking region companion (verified in
`audit/capture-explicit-stringregion/refined-checks/before/roots.txt`,
function 12: `effects: may_error=true may_gc=true`). So the new internal
region companion is, correctly and unsurprisingly, `may_gc=true` too
(`audit/capture-explicit-stringregion/refined-checks/after/roots.txt`,
functions 11/19) -- **not a regression, and not something to force to
false**: the milestone's own #22 speculated it "should plausibly be
may_gc=false", and the honest answer, confirmed from actual NIR rather than
assumed, is that it stays `true`, for a reason (`i+1`'s conservative
BigInt-overflow allocation bit) that predates this milestone entirely and
is common to *every* one-character accessor of this shape, virtualized or
not. Per the milestone's #25, no effect-analysis override was written to
force a different answer.

What *did* change is who calls into that safepoint, and from how far away:
before, every `scan_local`/`scan_label`/`scan_alpha`/`domain_loop` call to
`char_at`'s region companion carried a live closure register (rooted for
its own duration) across the call; after, the same call site carries the
captured `v` String directly (also rooted, but never wrapped in a Block
that itself needs a root, a header, and 8 bytes of capture-array payload).
Section "Root consequences" below quantifies the net effect on safepoints
and root candidates program-wide.

## GC/root lifetime

`v`, `char_at`'s sole capture, is now an ordinary managed (String)
parameter of `char_at`'s internal region companion and of every one of
`scan_local`/`scan_label`/`scan_alpha`/`tld_ok`/`domain_loop`'s own
internal variants (their captures flatten from `[n, char_at]` to `[n, v]`
-- see "NIR before/after" below). It is rooted exactly the way every other
managed parameter already is (`native/src/codegen/clif.rs`'s `def`: every
register, including a former capture, gets its own native-frame root slot
on definition) -- no new rooting mechanism, and, since a String is
immutable and `v` is never reassigned, no possible staleness. Verified
under `BOTLISH_NATIVE_GC_STRESS=1` (collect before every allocation):
`refined-checks.ir` itself (`blockescape-region-companion-refined-checks-4`)
and a dedicated adversarial fixture that calls the region companion and the
ordinary (materializing, allocating) internal variant of the same
virtualized `at` in the same self-tail loop iteration, back to back,
threading the same captured base String across many collections
(`blockescape-region-companion-gc-stress-1`) both produce the exact value
the reference interpreter and the unoptimized baseline agree on.

## `refined-checks.ir`: before/after evidence

### HIR/blockescape facts

Before: `char_at`'s binding was a `Bindings` *candidate* (locally bound,
non-duplicate, needs an environment, no forward-reference cell), and every
one of `RefsAsCalls`'s external/sibling reference checks passed -- the
*only* reason it was not in the final `eligible` set was the
`hir::stringregion::wants` guard. After: the guard is gone, so `char_at`'s
binding is `eligible`, `hir::blockescape::virtual` returns its callee
instance for both of `Emailish?`'s two specializations, and
`hir::blockescape::wants` includes both of `char_at`'s own specialize
instances.

### StringRegion facts (unchanged by this milestone)

`hir::stringregion::wants` was, and remains, `true` for both of `char_at`'s
instances -- `hir/stringregion.tcl` itself needed no change; it is simply
now *composed with*, rather than excluding, blockescape's own proof.

### NIR before (function 12, `char_at`'s canonical region companion, one instance)

```

    %1 = capture 0
    %2 = int 1 @e327
    %3 = rawint 1
    guard int %0 "+" @e324
    %4 = op iadd %0 %2 @e324
    guard int %0 "substring" @e320
    %5 = op regioncheck %1 %0 %4 @e320
    retmulti %1 %0 %4
end
```

...called from `scan_local`'s own body via `callenvmulti`, with a *real*
Block register (`%2`, `scan_local`'s own `char_at` capture) as the
environment operand:

```
%5 %6 %7 = callenvmulti 12 %2 %0 @e385
```

and, at the Cranelift IR level
(`audit/capture-explicit-stringregion/refined-checks/before/clif.txt`,
function 12), the environment load this milestone eliminates is visible
directly:

```

```

### NIR after (function 11, `char_at`'s internal region companion, same instance)

```

    %2 = int 1 @e327
    %3 = rawint 1
    guard int %0 "+" @e324
    %4 = op iadd %0 %2 @e324
    guard int %0 "substring" @e320
    %5 = op regioncheck %1 %0 %4 @e320

...called from `scan_local`'s own body via a direct `callmulti`, with `v`

```
%5 %6 %7 = callmulti 11 %0 %2 @e385
```

No `capture 0`, no environment operand, no `load.i64 ...+32` in the
Cranelift IR: `v` arrives as an ordinary incoming parameter register.

### Flattened captures after

`scan_local`/`scan_label`/`scan_alpha`/`tld_ok`/`domain_loop` (both
specialize instances of each) flatten from `[n, char_at]` to `[n, v]`,
confirmed directly from the emitted NIR function headers:

after:  func 12 "scan_local" params=3 env=0 ... pnames="i n v"        captures=0 ...

(and identically for `scan_label`, `scan_alpha`, `tld_ok`, `domain_loop`,
both instances each -- `tests/native-block-escape.test`'s

```

## Function/variant-count and duplicate-body check (#40)

`char_at` has two used specialize instances both before and after this
milestone (one per literal String `bench/refined-checks.ir`'s `check`
recurses over) -- an existing, unrelated specialization fact this milestone
does not change. Before: 2 instances × 2 function kinds (canonical +
canonical region companion) = 4 functions. After: 2 instances × 1 function
kind (internal region companion) = 2 functions. The two internal region
companion bodies (functions 11 and 19) are structurally identical NIR
(same op sequence, same operand shapes) differing only in their own
`@e<N>` source-position annotations -- exactly the same "one function per
specialize instance, same shape, different constant-folded literal"
pattern `scan_local`'s own pre-existing ×2 instances already have. This is
ordinary per-instance specialization, not variant explosion: no candidate
in this corpus produces more than one internal region companion per
specialize instance, and no equivalent-body duplication was introduced.

## Answers to the milestone's 26 questions

1. **What exact architectural mismatch forced `char_at` to remain
   materialized?** The only StringRegion result companion that existed
   (`RegionCompanionFunction`) was reached exclusively through
   `callenvmulti`, which reads `capture 0` out of a real `ClosureObj`. A
   capture-explicit candidate has no such object by definition, so it
   could not supply that one calling convention -- not a correctness
   limitation of the candidate itself, but a missing composition between
   two orthogonal representation choices.
2. **What new function variant was added?** `internalregion`
   (`InternalRegionCompanionFunction`/`InternalRegionCompanionRef`): the
   same instance and body as the existing `region` companion, but env=0
   with flattened captures as ordinary trailing parameters, exactly like
   `internal`.
3. **Special case or general composition?** A general composition: it is
   generated for any used instance that is simultaneously
   `hir::blockescape`-wanted and `hir::stringregion`-wanted, proven by the
   same two existing, name-independent analyses. No `char_at`, `Emailish?`,
   or `web.tcl` string appears anywhere in the new code.
4. **How is the variant identified and cached/reused?** By
   `(InstanceId, "internalregion")`, the same `Key`/`Placeholder` scheme
   every other variant uses, built at most once and shared by every call
   site through the existing `pending`-work-list mechanism -- no new
   identity or caching scheme was needed.
5. **What captures does `char_at`'s internal region companion receive?**
   Exactly `v` (the captured base String) -- the same flattened capture
   list its ordinary internal variant would use (and does use, on the
   fixtures where one exists), computed once by `hir::blockescape::captures`
   and consulted by both.
6. **Does it have an env register?** No -- `env=0`, confirmed directly in
   the emitted NIR header (`env=0 ... captures=0`) and in the Cranelift IR
   (no `load.i64 ...+32` "capture 0" sequence anywhere in its body).
7. **How do `scan_local`/`scan_label`/`scan_alpha`/`tld_ok`/`domain_loop`'s
   capture lists change?** All five flatten from `[n, char_at]` to
   `[n, v]`, verified directly from the emitted NIR (`pnames="i n v"`),
   for both specialize instances each.
8. **Does `char_at` allocate any Block at runtime now?** No --
   `rt_closure_new`/`closure ` for `char_at` is gone from the NIR;
   `refined-checks.ir`'s own allocation report shows 0 Block allocations
   attributable to `char_at` (the single surviving Block is
   `web::uri_escape_text`'s unrelated module-startup closure).
9. **Are both recurrent 800/400 allocation sites gone?** Yes: Block
   allocations for the whole program go from 1,201 to 1; the 800+400
   sites this milestone specifically targeted are both eliminated.
10. **Does any ordinary String-producing `char_at` call still work?** Yes
    -- `refined-checks.ir` itself never needs one (every call site is
    region-eligible), but the dedicated mixed-fixture tests
    (`blockescape-region-companion-mixed-*`) prove a virtualized closure's
    ordinary-result callers keep working, dispatched to the pre-existing
    `internal` variant, unaffected by this milestone.
11. **Can a source Block simultaneously have canonical/materialized and
    capture-explicit-region callers?** At the whole-program level, yes
    (`blockescape-region-companion-escaping-coexist-*`: one closure
    escapes and keeps its canonical closure/region-companion machinery,
    a different closure in the same program is virtualized and served
    through the new internal region companion). A *single binding* cannot
    itself have both an escaping and a virtualizable reference --
    `hir/blockescape.tcl`'s `RefsAsCalls` declines the moment any
    reference is not an exact call, unchanged by this milestone -- so
    "mixed callers of the very same binding" means ordinary-vs-region
    (both capture-explicit), not materialized-vs-virtual.
12. **Are canonical entries retained where semantically necessary?** Yes:
    `Function`/`RegionCompanionFunction` are still unconditionally
    available for any caller that resolves to them (a generic/indirect
    call, or a genuinely escaping binding); they simply go unbuilt when
    nothing ever references them (`refined-checks.ir`'s own `char_at`),
    via the same reachability accounting that already dropped unused
    functions before this milestone.
13. **Is the internal region companion `may_gc=false`?** No, for
    `char_at` specifically: its own `i+1` lowers through `IAdd`, which
    `op_may_allocate` conservatively marks allocating (BigInt-overflow
    promotion) -- and that bit was *already* `true` on the old canonical
    region companion before this milestone (verified in the "before"
    roots report). Not a regression; the composition itself introduces no
    new allocation.
14. **If so, do its call safepoints disappear automatically?** They do
    not disappear at `char_at`'s own call sites (still `may_gc=true`,
    unchanged from before), but total safepoints across the *whole
    program* drop from 73 to 65: the reduction comes from no longer
    rooting a `char_at` closure register across every call site that used
    to carry one, not from `char_at`'s own frame becoming safepoint-free.
15. **How many safepoints/root obligations disappear?** 8 safepoints, 12
    root candidates, 6 native-frame root slots, 4 entry-zero slots
    (summed across all 25/27 functions; see the allocation-and-structural-
    evidence table above).
16. **Does F3/F3b need any manual change?** No -- `summarize_call_effects`
    (Rust) is entirely generic over NIR op tables and the call graph; the
    new function participates automatically, with zero Rust source
    changes.
17. **Does the input String `v` remain correctly rooted under GC stress?**
    Yes -- confirmed both on `refined-checks.ir` itself and on a
    dedicated adversarial fixture that interleaves region and
    materializing (allocating) calls to the same virtualized closure
    inside a self-tail loop, under `BOTLISH_NATIVE_GC_STRESS=1`.
18. **Is scanner self-tail lowering still a direct loop with `v` as
    loop-carried state?** Yes -- `tail`-instruction count is unchanged
    (11 before, 11 after), `tailenv` remains 0, and `v` is now one of the
    ordinary registers each `tail` backedge re-passes every iteration.
19. **How many Block objects remain in `refined-checks.ir`?** 1 (the
    module-startup `web::uri_escape_text` closure, explicitly out of this
    milestone's scope).
20. **What is the new total managed allocation profile?** 15 objects
    total: 9 String + 5 List + 1 Block -- exactly the milestone's own
    hypothesized target, reached without forcing it.
21. **What is the current `refined-checks.ir` machine-code size?** 17,772
    bytes (down from 18,894; −5.9%).
22. **What is its current runtime versus Rust and Go?** Cranelift 464.25
    us vs. Rust 130.75 us vs. Go 197.24 us, best-of-5 -- Cranelift remains
    slower on this recursion/guard-heavy benchmark, essentially unchanged
    in relative shape from before this milestone (structural, not a
    performance-parity milestone).
23. **Did any other corpus program change?** No -- verified directly
    (allocation totals, machine-code bytes, function counts, and output
    values byte-for-byte identical) for all 12 other corpus programs.
24. **Did composing these two variant systems reveal a broader
    function-variant abstraction problem to record for later?** A mild
    one: this file's variant table now has six modes
    (`canonical`/`companion`/`region`/`internal`/`internalregion`/
    `fields`/`fieldscompanion` -- seven, counting `fields`'s own
    companion), each hand-written as a near-duplicate of
    `Function`/`InternalFunction`'s parameter-setup loop and
    `CompanionFunction`/`RegionCompanionFunction`'s own body-ending choice.
    `InternalRegionCompanionFunction` itself is a mechanical splice of the
    two (visible directly in its source: the parameter/capture setup is
    copied verbatim from `InternalFunction`, the body-ending verbatim from
    `RegionCompanionFunction`). A `fields`+`region`
    ("capture-explicit-fields-taking region companion") cell is still
    empty in the same cross-product and would need the identical splice
    again if ever demanded. This milestone deliberately did not build a
    generalized variant-composition framework (the brief's own #39/#61
    scope limit) -- but if a *third* orthogonal dimension is ever needed,
    factoring the shared parameter-setup and body-ending helpers this
    milestone's own procs duplicate (rather than a fourth hand-copied
    proc) is the natural next step, worth a small follow-up if that need
    materializes.
25. **What is now the dominant remaining String/Bytes/construction cost?**
    `refined-checks.ir` itself has none left worth naming (9 String + 5
    List objects total, once per program run, not per-scan). Corpus-wide,
    the largest remaining *recurrent* construction sites are unrelated to
    this milestone and to `char_at`: `ai_text_clean` (111 objects, 110
    String + 1 List) and `csv_records` (83 objects, 18 String + 11 List +
    54 MutableArray) are the biggest absolute counts in the 13-program
    corpus, both already
    surveyed by the String-view milestone's own consumer taxonomy (classes
    E/F: UTF-8 encode and escaping/stored/returned substrings -- correctly
    materializing, not a StringRegion gap).
26. **Should the next milestone move to Utf8Bytes/construction/concat, and
    which site should lead it?** Not evaluated in depth here (explicitly
    out of this milestone's scope, per its own #26/#57-60) -- but if asked,
    `ai_text_clean`'s repeated `encode_utf8 -> List[Int]` site is the
    largest single measured recurrent-allocation candidate left in the
    corpus and the most concretely scoped starting point, consistent with
    the String-view milestone's own #57 prediction.
